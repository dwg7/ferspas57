# Handover Notes

Read this first in any new session on this repo.

## What's true as of 2026-09-03 (updated: first real conversions built and verified; batch scope approved; client-map decisions made; hosting still not finalized)

- **Real, working PMTiles/GeoJSON files now exist locally** (not yet uploaded anywhere): `gaez-aez33.pmtiles`, `gaez-aez57.pmtiles`, `hih-cod-maize-score.pmtiles`, `hih-cod-maize-final.geojson`. The full COG→PMTiles pipeline (official-colormap-or-own-ramp → GDAL color-table VRT → MBTiles with forced `RESAMPLING=NEAREST` at every step → `gdaladdo` pyramid → `pmtiles convert`) is validated end-to-end and visually confirmed in a local MapLibre test. See `DECISIONS.md` **D7–D11** for the full trail of gotchas found along the way (GDAL's MBTiles driver needs an explicit overview pass or it writes only one zoom level; resampling defaults must be pinned to nearest-neighbor at *every* step, not just the pyramid step, or categorical/discrete data silently corrupts; WebP has no true-lossless option in GDAL's writer, disqualifying it for this data regardless of size). **Batch-converting the remaining 6 DR Congo commodities + 3 accessibility layers with this same pipeline is approved (D11)** — that's the immediate next task, not a re-decision.
- **HIH's two data shapes need two different treatments, discovered by actually inspecting the real COGs, not assuming from STAC metadata**: `LOCATIONSCORE`/`SCORE` layers are continuous Float32 with a *hidden* `-9999` sentinel value on top of the declared NoData (about half of "valid" pixels in the one checked so far) — must be masked and given a fixed 0–100 domain, not a per-file auto-stretch. `FINALLOCATION` layers are near-binary Int16 with only a tiny handful of real "selected site" pixels (417 of ~18M in the one checked) — too sparse for raster tiling to survive downsampling, so these are being converted to **vector** (GeoJSON polygons via `gdal_polygonize.py`), not PMTiles, reversing D9's original all-raster assumption. Full detail in `DECISIONS.md` **D10**.
- **Client-map design decisions are set, implementation not yet done**: MapLibre **globe projection**, not flat Mercator — directly motivated by Togo's African-Union-backed resolution going to a UN General Assembly vote in September 2026 demanding institutions abandon the Mercator projection because it visually shrinks Africa (confirmed real via WebSearch, not assumed); **Positron** as the default basemap style; `attribution` embedded in every PMTiles archive's own metadata (not wired up separately client-side); the info/legend panel should be collapsible. None of these are implemented in the local test page yet. See `DECISIONS.md` **D11**.
- **Naming is finalized for the current batch** (`DECISIONS.md` **D9/D10**): flat, Martin-culture-style, no directory nesting — `gaez-aez33`, `gaez-aez57`, `hih-access-{urban,urban-weighted,port}`, `hih-fishfarm-{closed,closed-final,open,extensive}` (country-agnostic names, DR-Congo-only data for now, meant to gain other countries' data later without renaming), `hih-cod-{cassava,cocoa,coffee,maize,palmoil,wheat,livestock}-{score,final}`. `stars-fd` already checked all 23 names against `config/martin.yaml` and `depot.optgeo.org` — **zero collisions**, no strict naming convention is enforced there either.

- **Repo just founded**, scaffolded by a Claude Code session working in `dwg7/staccato-ecosystem` at hfu's request. Only doc scaffolding exists (`README.md`, `CLAUDE.md`, `HANDOVER.md`, `DECISIONS.md`, `LICENSE`) — still no code, no ingestion pipeline. But the catalog has now been fully surveyed and the tile-serving architecture question has been investigated in depth (see `DECISIONS.md`'s **D2**, currently open/undecided) — this is no longer a cold start.
- **Founding issue**: [`UNopenGIS/7#997`](https://github.com/UNopenGIS/7/issues/997), a child of [`#932`](https://github.com/UNopenGIS/7/issues/932) (the original DWG5×DWG7 exploration) and related to the meta-issue [`#995`](https://github.com/UNopenGIS/7/issues/995).
- **The FERSPAS STAC endpoint is live and reachable**: `https://data.review.fao.org/geospatial/search/stac/collections`. As of 2026-09-03, paged through fully (token-based `next` link): **1282 collections total** — substantially more than the ~157 hfu manually surveyed and summarized in `#932` in June 2026. **The June summary is now confirmed stale in at least one concrete way** (see Niedersachsen DOP below) — don't rely on it for anything beyond historical context.
- **License is recorded per collection**, as a `links` entry with `"rel": "license"` pointing at a URL (e.g. `https://creativecommons.org/licenses/by/4.0/`). Some collections carry no license link at all — treat those as unresolved/needs-asking, not as implicitly open.
- **No orthophoto/DOP collection exists anywhere in the catalog** — confirmed by keyword search (`ortho`, `dop`, `aerial`, `imagery`, `photo`, `drone`, `uav`, `basemap`, `vhr`, etc.) across **all 1282 collections**, not just a sample. This is now a settled finding, not a gap to re-check.
- **The Niedersachsen DOP dataset is confirmed gone.** hfu's `#932` June 2026 comment described it precisely: German high-res orthophoto (DOP RGBI 20cm, 2012–2025 time series, Niedersachsen state), provided externally by LGLN (Landesamt für Geoinformation und Landesvermessung Niedersachsen) under CC-BY-4.0, present in FERSPAS's catalog *then* as an external reference entry (not FAO's own data). It does not appear anywhere in the current 1282 — by ID, keyword, or provider name. It was real, it was in FERSPAS, and it has since been removed. Do not go looking for it again without a specific reason to think it's back.
- **Catalog structure is far more homogeneous than STAC-the-spec would suggest.** Sampling one item per each of the 33 top-level `fao-gismgr:*` sub-catalogs (`WAPOR-3` [668 collections, over half the catalog], `GLOSIS`, `HIH`, `GAEZ-V5`, `GDVI`, `C3S`, `FAOSTAT`, `EOSTAT`, `CRTB`, `ASIS`, `CHIRPS`/`CHIRPS-V3`, `DIGICHILD`, `AI-DST`, `FUZ-CAS`, `AQUAMAPS`, `GLW`/`GLW3`/`GLW4`/`GLW4-2020`, `AQUASTAT`, `BTN-FCO`, `ESA`, `GLEAM3`, `ECOSYS`, and several singletons) found **zero vector assets** and a uniform `data` (COG) + `preview`/`thumbnail` (WMTS PNG) asset pattern everywhere. FERSPAS content is overwhelmingly *derived/analytical* rasters (climate, soil, water productivity, crop masks, disease risk, livestock density) — not raw imagery of any kind.
- **FAO already runs its own tile server in front of every COG**: `https://data.apps.fao.org/map/wmts/wmts`, which self-identifies via `GetCapabilities` as "FAO WMTS WRAPPER" (provider: FAO CSI, contact: Mohamed Megahed — the same team behind the June 2026 DWG5 presentation). It serves the standard `GoogleMapsCompatible` Web Mercator grid (256px tiles, z0–z24) and was confirmed working across layers from six different sub-catalogs. Full technical detail, measured performance (200ms–4s/tile, no edge caching per `cf-cache-status: DYNAMIC`), and the underlying COG's structure (confirmed well-formed with a 15-level overview pyramid, range-request-capable, but **no CORS configured** on its GCS bucket) are in `DECISIONS.md`'s **D2**.
- **The tile-serving architecture decision is open, not settled.** Four options are on the table (direct COG access blocked by CORS today; mirroring the raw COG elsewhere with CORS as a deliberately temporary "technical hostage" per hfu; self-generated zoom-capped PMTiles; or living with FAO's WMTS wrapper for prototyping only) — see `DECISIONS.md` **D2** for the full reasoning. **Do not pick one and start building without checking with hfu first** — this was explicitly left open on 2026-09-03 pending (a) confirming what hosting platform hfu meant by "stars", (b) a per-collection file-size/zoom-cap feasibility pass for the PMTiles option, and (c) a view on whether/how to raise the CORS gap with FAO CSI.

## The technical starting point

- `staccato-spec`'s [`catalog-integration.md` §10](https://github.com/UNopenGIS/staccato-spec/blob/main/spec/catalog-integration.md) already commits to the approach this repo should follow: treat STAC as a source to convert *from*, not as Cartographer's primary discovery model; materialize a TileJSON-shaped, `martin catalog`-compatible representation at ingestion time.
- [`hfu/layers-martin`](https://github.com/hfu/layers-martin) is the concrete precedent to study and structurally mirror: it statically generates a Martin-compatible `/catalog` (source list) and `/{sourceID}` (TileJSON) from GSI's `layers.txt`, hosted on GitHub Pages, referencing existing tile URLs rather than duplicating tile data. Read its README and code before designing this repo's STAC equivalent — the goal is the same output shape (`/catalog` + `/{sourceID}` TileJSON), different input (STAC Collections/Items instead of `layers.txt`).
- FERSPAS's STAC assets are, uniformly as far as sampled, COGs (Cloud-Optimized GeoTIFFs) fronted by FAO's own WMTS wrapper — see the 2026-09-03 findings above and `DECISIONS.md` **D2**. This is now measured, not speculative: don't re-derive it from scratch, but do re-verify against the specific collection(s) actually chosen, since only one item per sub-catalog was sampled.
