### D48 — Mass production: 355 machine-generated per-site narrative profiles, indexed in `data/narratives-index.json`; the D45 "300-entry lookup" design gap closed, not deferred further
**Date**: 2026-09-05
**Status**: Done. All 355 entries generated, round-trip-verified, and one confirmed working end-to-end in-browser. `NARRATIVES.md`/`STAFF-PROMPT.md` updated to describe the resulting two-tier library.

**hfu's go-ahead**: "量産に入ってください" (start mass production), after D45 set the 70/30 strategy and D46/D47's UI work. This entry is the actual production run.

**A scope decision made before generating anything**: D39 settled `NARRATIVES.md` as English-only, with Staff doing live translation — the Japanese profiles drafted earlier in this session (the Beni livestock example and four others, plus a 23-step Japanese "cocoa tour") were explicitly a Staff-roleplay demonstration of D42's live-link mechanism, not library content. Mass production regenerates equivalent content in English, matching the Library's own established convention, rather than reusing that Japanese text directly.

**What "per-site profile" ended up meaning at scale**: rather than one narrative per commodity (13 possible, exhausted per D45) or one narrative per individual site as 355 separate files (unwieldy — hundreds of near-identical small files), each of the 357 real FAO-selected sites became one entry in a single structured index, `data/narratives-index.json`. Two sites (`civ_cereal`#7, `civ_vegetables`#10) were excluded — the same `-999` hidden-sentinel sites D41 already found — leaving **355 entries**. Each entry carries `country`/`commodity`/`rank`/`site_count`/`score`/`aez33_class`/coordinates, a plain-English `title`, the full plain `narrative` document, and an already-encoded, already-round-trip-verified `link` — usable immediately, no further processing.

**Generation pipeline** (mechanical, no discovery, no per-entry creative cost — this is what makes 355 practical where D41's commodity-level sweep topped out at 13):
1. A Python template reads `data/site-scores.json` (D45's captured dataset), and for every real site produces a 2-step narrative: step 1 shows the site's real GAEZ AEZ33 classification (English class names from the same FAO-guide-verified table `docs/aez_legend.js` already uses, D13); step 2 overlays the real score and states honestly where it ranks (`"the highest score"` / `"the Nth-highest score"` / `"the lowest score"`) among that commodity/country's other real sites — every number traces directly to a `gdallocationinfo` reading already captured in D45, nothing newly measured or invented.
2. A Node script loads `lz-string@1.5.0` once, then encodes and round-trip-verifies all 355 documents in a single process (avoiding 355 separate network fetches) — 0 failures on the actual run.
3. Spot-checked several entries against numbers already independently verified earlier in this project: `cod`/`maize` rank 1 came back exactly **65.5**, matching D13's original hand-verified "site FAO actually selected" score; `caf`/`cassava` rank 1 came back exactly **77.3**, matching this session's earlier manually-verified example. One entry (`caf`/`cassava` rank 1) played back correctly end-to-end in-browser from its raw encoded link, not just checked as data.

**The D45 "closing note" gap — addressed now, not deferred again**: D45 flagged that `NARRATIVES.md`'s flat-Markdown-scanned-in-the-prompt design would break at ~300 entries, and explicitly warned against discovering this only after the fact. Resolved by splitting the library into two tiers, documented in both `NARRATIVES.md` and `STAFF-PROMPT.md` (bumped to tag `ferspas57-staff-2026-09-05e`): the existing small curated set (3 "divergence" stories) stays embedded directly in `NARRATIVES.md`, reachable by any Staff including a genuinely tool-less one; the new 355-entry index lives in `data/narratives-index.json` and is reachable only by a Staff with real code execution and network access (fetching it directly, same capability-conditional design D42 already established for narrative-link generation) — a tool-less Staff is instructed to say plainly when a question can only be answered from this larger tier, rather than guess at its contents.

**Not done this pass**: the 21-real-site "tour" format tested earlier (one narrative covering many sites in sequence) was a useful scale test but isn't part of this production run — the per-site index covers the same underlying data more granularly. Building curated multi-site tours as a third, smaller content type remains a real, un-pursued option if hfu wants it later.

### D47 — UI design review: the "Scores" panel replaced by a radial, icon-based, mobile-liquid widget; narrative playback now suppresses redundant/English-only chrome
**Date**: 2026-09-05
**Status**: Done. Reviewed against a real screenshot hfu shared of the live D46 build; all changes verified in-browser (this session's browser tool has a known limitation faithfully emulating viewport width for page JS — verified the responsive formula directly instead, see below).

**hfu's screenshot flagged a real problem, not just an aesthetic one**: a black AEZ-classification tooltip (`aez_legend.js`/`aez57_legend.js`) floats at the map's screen center — right where the probe ring sits, right above the narrative panel. During narrative playback this is doubly wrong: (1) redundant — the caption already explains the classification in its own prose; (2) a real language-agnostic-chrome violation — the tooltip's text (`AEZ33 — 7: Subtropics, warm — semi-arid`) is hardcoded English pulled from `AEZ33_CLASS_NAMES`, so it sits directly on top of a Japanese-language narrative, the exact failure mode D40/D43 already fixed elsewhere in this same UI. Separately, hfu named the "Scores" side panel (`score_probe.js`) as the more persistently annoying element, and — after D46 made every panel's text 1.6x larger — the top-right corner had also become genuinely crowded (narrative/paste-box buttons + MapLibre's zoom control + a now-larger Scores list all stacked in one corner).

**Fixes applied**:
1. **AEZ/AEZ57 tooltips now hide whenever a narrative is active** (`document.getElementById("narrative").classList.contains("active")`), in both `aez_legend.js` and `aez57_legend.js`. The existing `moveend`→`scheduleSample` hook already re-fires on every narrative step (each step calls `map.flyTo()`), so no extra event wiring was needed — the guard alone is sufficient.
2. **MapLibre's `NavigationControl` (zoom +/−, compass) moved from top-right to bottom-right** (`map.addControl(new maplibregl.NavigationControl(), "bottom-right")`), pairing with the attribution control already there and freeing the top-right corner down to just the two custom buttons (▶ narrative, 📄 paste-box).
3. **The "Scores" list rebuilt as a radial widget, centered on the probe point itself, not a boxed side panel** — hfu's own reference (a radial/compass-style control, a fixed center with items arranged evenly around it) plus an explicit ask for a chart-like, area-saving layout. Implementation, in `score_probe.js`:
   - Each valid score becomes one circular icon-bubble positioned by trigonometry (`angle = -90° + i·360°/n`, clockwise from 12 o'clock) around the existing probe ring — no separate panel chrome at all.
   - **Language-agnostic by construction, not by afterthought**: each `SCORE_SOURCES` entry gained an `icon` (a pictogram emoji — 🍠 cassava, 🍫 cocoa, ☕ coffee, 🌽 maize, 🌴 palm oil, 🌾 wheat, 🐄 livestock, 🌿/🍎/🥬/🥛 for CIV's cereal/fruits/vegetables/dairy, 🐟/🐠/🎣 for the three fish-farming systems, 🏙️/🏘️/⚓ for the three accessibility layers) and, for the seven per-country commodity entries, a real Unicode country flag (`🇨🇩`/`🇨🇫`/`🇨🇮`) as a small corner badge — needed because e.g. cassava exists for both COD and CAF and an icon alone can't disambiguate. None of this is a literal claim about the data (there's no dedicated "cassava" emoji; this project already accepted similarly approximate pictograms for narrative playback controls, D40) — it's a recognizable, consistent stand-in, with the exact English label preserved only as a hover `title` tooltip, never drawn on screen.
   - **Color management, addressed as hfu asked, not left implicit**: the score value is encoded through three *independent, redundant* visual channels rather than color alone (a real colorblind-accessibility concern, not just a stylistic one) — (a) the bubble's border color, drawn from `scoreRampColor()`, the *exact same* ramp the raster tiles themselves already use, so the widget never introduces an independent color meaning; (b) the bubble's diameter, larger for a higher score; (c) position — bubbles are sorted highest-first starting at 12 o'clock going clockwise, so top-ranked entries always cluster near the top regardless of a viewer's color perception.
   - **Liquid/mobile-responsive, per hfu's explicit request**: ring radius and bubble sizes are computed from `Math.min(window.innerWidth, window.innerHeight)` (a `vmin`-equivalent), clamped to `[60, 150]`px, recomputed on `window.resize` (using the last-fetched scores, not a re-probe) and whenever the narrative panel's `active` class changes (via a `MutationObserver`, since narrative start/stop isn't otherwise an event this file can hook). Verified the formula directly with a mocked `375×667` viewport (radius 82.5px, comfortably clear of the screen edge) vs. the default desktop clamp (150px) — this session's browser tool does not faithfully propagate emulated viewport dimensions to page JS (a tooling limitation noted before, e.g. D33), so the formula was checked by substitution rather than genuine device emulation; the logic itself does not depend on that tool's fidelity.

**Verified in-browser**: 13 bubbles rendered correctly for a DR Congo point (`Access: urban` topmost at 100, dark ramp color, matches sort-by-value-descending), 9 for a Côte d'Ivoire point with the `🇨🇮` badge present; both the radial widget and the AEZ tooltip confirmed hidden immediately on `startNarrative()` and remaining hidden through a subsequent pan; the zoom control confirmed present under `.maplibregl-ctrl-bottom-right` and absent from `.maplibregl-ctrl-top-right`.

**Deliberately not done this pass** (flagged in the design review, not pursued as over-engineering risk): consolidating the AEZ tooltip and this radial widget into one unified "inspector" UI, and any bigger navigation/layout overhaul beyond the three fixes above.

### D45 — Scaling `NARRATIVES.md` toward ~300: strategy set (70% honest per-site profiles, 30% commodity-level divergence stories); the full 357-site backing dataset captured and made durable
**Date**: 2026-09-05
**Status**: Strategy agreed; data-capture stage done. Narrative production itself (both buckets) not yet started.

**The scaling problem, stated plainly**: D41's "GAEZ-constrained land scores higher" divergence-story template is now exhausted at the *commodity* level — all 13 real commodity/country combinations in the current catalog (COD's 7, CAF's 1, CIV's 5) have been investigated, yielding 3 accepted narratives (maize, wheat, dairy) out of 13 attempts. That template cannot reach anywhere near hfu's stated target of roughly 300 narratives without new countries/commodities being added to the catalog first.

**hfu's question, and the honest answer**: hfu asked directly whether the existing narratives could be "made longer" by Staff itself, given hfu's own suspicion that this is exactly why `NARRATIVES.md` exists as a pre-authored library rather than a live-generation task. Confirmed: re-pacing/elaborating *already-verified* content (more steps, more explanation grounded in `BACKGROUND.md`'s already-vetted static knowledge) is safely Staff's live job, same as D39's language/register work — no new facts, only re-expression. But *discovering new facts* (a new site, a new score comparison) remains categorically not Staff's job, and D42's code-execution unlock doesn't change this: embedding `lz-string` was safe because it's a small (~4.8KB), exact, deterministic, already-vetted transform with a cheap verification step (round-trip decode); reading a real Cloud-Optimized GeoTIFF correctly requires GDAL-equivalent tooling that can't be safely embedded the same way, and D41's own "trust but verify" catch (a careful sub-agent's aggregate claim not surviving independent re-verification) is a direct demonstration of how easily this goes wrong even with real tooling and real intent — asking a live, unverified Staff to attempt it would be squarely the kind of invisible-failure risk Anti-Fabrication exists to prevent.

**The scaling strategy agreed**: shift the *unit of production* from "commodity" (13 possible, exhausted) to "individual real site" (357 possible, see below) for the bulk of the library, reserving the commodity-level "divergence mystery" template (D13/D41's style) for a smaller, deliberately curated set. Split: **~70% honest per-site profiles, ~30% commodity-level divergence stories** (hfu's own ratio). A per-site profile doesn't need a surprising pattern to justify its existence — it just needs to be accurate: real coordinates, real GAEZ class, real HIH score, one sentence grounding the result in HIH's documented multi-criteria methodology (`BACKGROUND.md` §4). This raises the practical yield from D41's ~23% (needs a genuine surprise) to essentially 100% of real sites (needs only accuracy) — see the worked example below.

**Worked example (not yet added to `NARRATIVES.md`, a format proof only)**: a 2-step profile for one real DR Congo livestock site at Beni (29.4424, 0.4984) — GAEZ class 32 (urban/built-up, not even an agricultural classification), HIH score 66.2 (one of the 16 selected sites' highest) — explained via HIH's accessibility-over-agronomy multi-criteria design. Both numbers independently re-verified against the live COGs before drafting. hfu confirmed this direction; the concrete template (step count, tone) is still open to refinement once volume production actually starts.

**Data-capture stage, done today**: before any narrative production, captured and made durable the real per-site dataset the whole 70% bucket depends on — every one of the 357 real FAO-selected final-location sites across all 13 commodity/country combinations, with its real GAEZ AEZ33 class and real HIH suitability score, verified via `gdallocationinfo -wgs84 -valonly` against the actual live source COGs (STAC-resolved asset URLs, all confirmed reachable via `curl -I` before use). Ran as 14 batched `gdallocationinfo` processes (one per raster — 13 commodity score rasters + one shared GAEZ AEZ33 raster — each fed every relevant site's coordinates via stdin in one process invocation, not one process per point, per the D41 sub-agents' own established technique) — completed in well under 4 minutes for all 357 sites × 2 rasters each, versus the many-minutes-per-commodity cost the D41 investigation agents incurred doing this less efficiently. Cross-checked a sample of results against numbers already independently verified earlier in this session (the Beni urban site's 66.2/class 32, the wheat top scorer's 60.89/class 25, the CIV dairy score range 68.6–74.8) — all matched exactly. Also independently reproduced D41's two `-999` hidden-sentinel sites (CIV cereal site 8, CIV vegetables site 11, both near Agnibilékrou) without being specifically told to look for them, confirming the capture is complete and correct, not just fast.

**Saved to `data/site-scores.json`** (new, repo root) — this project's first data file outside `samples/*.json`'s narrative documents. Structured per `<country>_<commodity>` key with `site_count`, the source COG URLs used, and each site's `{index, lon, lat, aez33_class, score}`; a `_meta` block documents provenance (capture method, date, purpose) and flags the two known sentinel sites explicitly, so nothing downstream mistakes `"-999"` for a real score. This is now the reference dataset for both narrative buckets going forward — regenerate it (same script logic, not preserved as a committed script yet) rather than re-deriving numbers ad hoc if the underlying GeoJSON/COGs ever change.

**Explicitly flagged, not yet solved**: at ~300 entries, `NARRATIVES.md`'s current design (a flat Markdown list Staff scans inline in its own system prompt) stops working — embedding 300 entries' worth of descriptions directly in `STAFF-PROMPT.md` is impractical. This needs its own design pass (a lighter index Staff can search rather than fully embed, possibly via the same D42 code-execution path) before or alongside actual mass production — noted here so it isn't discovered only after 300 files already exist in an unfindable shape.

### D44 — Cartographer's paste-box now also accepts a dropped file, alongside paste
**Date**: 2026-09-05
**Status**: Done, verified in-browser for both a dropped narrative JSON and a dropped Map Intent YAML file.

**hfu's design question**: for the tool-less/no-code-execution fallback (D42's "if lz-string isn't available, what then?"), hfu proposed: Staff shows the translated/adapted narrative as a plain code block, and Cartographer accepts it either pasted or dropped as a file. The paste half was already exactly D39's existing design; the drop half was new.

**Assessment and implementation**: adding file-drop support is a cheap, low-risk complement to the existing paste-box, not a new format or a new judgment call — it's just another way to get the same plain-text content into the same textarea, reusing the exact same auto-detect/parse/apply logic (`docs/map_intent.js`) unchanged. Refactored the Apply button's inline handler into a shared `applyPastedText()` function, then added `dragover`/`drop` listeners scoped to the textarea itself: a dropped file's contents are read via the File API, written into the textarea (for visible feedback), and run through the same `applyPastedText()` call the Apply button uses. No new dependency, no new schema, no Cartographer capability that didn't already exist for paste.

**Verified in-browser**: dispatched a synthetic `drop` event carrying a real `File` (via `DataTransfer`) for both a narrative JSON (`samples/narrative-cod-wheat-highlands.json`) and a Map Intent YAML snippet — both correctly auto-detected, applied, and closed the overlay, identically to the paste path.

### D42 — Staff can now hand over a real `#narrative=` link for a translated/adapted narrative, when it has genuine code execution
**Date**: 2026-09-05
**Status**: Done. `STAFF-PROMPT.md`/`NARRATIVE-FORMAT.md` updated; the exact recipe end-to-end-tested against all 3 real narratives with a real Japanese translation.

**hfu's pushback**: after seeing this session directly demonstrate Japanese-translated narratives by running `scripts/encode-narrative.mjs` (i.e., real code execution producing a real link), hfu flagged that `STAFF-PROMPT.md`'s blanket "you have no code execution" framing — and the resulting "translated narratives can only ever be paste-box JSON" design (D39) — was leaving real capability on the table. hfu's framing: a generative AI directly producing a working URL is "a fairly core point," worth solving properly rather than accepting the paste-box regression as final. (hfu also named the actual history here: paste-box-only *is* how the original "faceless-cartographer" concept worked, and it evolved into URL-embedding specifically because copy-paste was too much friction — so settling back onto paste-box-only for anything beyond the as-authored English narrative would have been a real regression, not merely a limitation.)

**Why the original constraint existed, and why it doesn't have to apply universally**: `#q=` (D32) was built assuming the worst case — chukei's real deployment (a GenAI portal chat with no plugin/tool access at all) genuinely cannot compute LZString compression through token generation alone; a compression algorithm involves exact bit-packing and dictionary state that an LLM cannot reliably reproduce character-by-character without actually running it, and a single wrong byte silently breaks the link with no error surfaced (the same asymmetric fabrication risk Anti-Fabrication already calls out for a bad `source_id`). That worst case is real and `#q=`'s design for it is unchanged and still correct. But this project had been treating "no code execution" as Staff's universal condition, when it's actually just the *minimum* case the prompt needs to keep working for — plenty of real Staff runtimes (Claude with code execution, ChatGPT Code Interpreter, custom GPTs with Actions, and — as directly demonstrated in this very session — Claude Code itself) do have a real, network-capable code-execution tool, and forbidding its use when genuinely present was needlessly conservative.

**The fix**: `STAFF-PROMPT.md`'s opening paragraph now states the prompt works with zero code execution, but that Staff should use a real one if its actual runtime provides it. A new "Computing a real narrative link yourself" subsection under Narrative Mode embeds the complete, byte-identical `lz-string@1.5.0` minified source (~4.8KB — small enough to embed directly, confirmed byte-for-byte identical to the exact file `docs/narrative.js`/`scripts/encode-narrative.mjs` already load from unpkg, so a Staff-computed link is guaranteed decoder-compatible) directly in the prompt text, with an exact, tested recipe: run the embedded library, call `LZString.compressToEncodedURIComponent(JSON.stringify(narrativeDoc))`, build the link, then **mandatorily round-trip-verify** (`decompressFromEncodedURIComponent` back to the original, `JSON.stringify` comparison) before presenting it — matching this project's standing "never trust a pipeline without checking its own output" discipline (D27, D35, D36, `encode-narrative.mjs`). Embedding the actual library (rather than fetching it, or worse, asking Staff to reimplement LZString from description) removes any network dependency and any risk of behavioral drift between what Staff computes and what the Cartographer's own decoder expects — it is the exact same file, not a reimplementation.

**Explicit safety framing, not just capability framing**: the new section repeatedly states this path is for genuine, verified code execution only, never for approximating the computation through reasoning — "even one wrong character silently produces a link this Cartographer's decoder cannot read, with no error shown to the user." If Staff has any doubt whether its code tool actually ran, or the round-trip check fails, the instruction is to fall back to the paste-box path (still the honest baseline for genuinely tool-less runtimes) rather than guess.

**Verified end-to-end, not just written**: extracted the exact embedded library and recipe code blocks from the committed `STAFF-PROMPT.md` text itself (not a separate copy) and ran them against real translated narrative documents — the same 3 Japanese narratives produced for this session's earlier demonstration (DR Congo maize, DR Congo wheat, Côte d'Ivoire dairy) — confirming byte-identical match to the real `lz-string@1.5.0` minified source and successful, round-trip-verified link generation for all three.

**What did not change**: `#q=`'s design (still assumes zero code execution, unconditionally hand-typeable) is untouched — this only affects the narrative-translation path, which was the one place the project had assumed a capability ceiling that doesn't universally hold. `docs/narrative.js`/Cartographer needs no changes at all (as already established, D39) — it already accepts a `#narrative=` link from any source, Staff-computed or pre-built.

### D39 — Reverted pre-baked multi-language narratives; settled design: English-only Library, Staff translates live via paste-box
**Date**: 2026-09-05
**Status**: Done. Supersedes D38's proposed `?lang=`/pre-generation design before any of it reached production — the pivot happened mid-implementation, after the `--lang` flag and a 10-language link table had already been built and were about to be committed.

**What was being built, and why it got stopped mid-way**: following D38's mandate ("narrative language is Staff's job"), the first concrete design was a `?lang=` query parameter plus a `scripts/encode-narrative.mjs --lang <code>` flag that mechanically flattened `NARRATIVES.md`'s one narrative into a separate pre-encoded link per language (10 links for the one existing entry). **hfu's objections, in the order raised**:
1. Pre-baking multi-language content into the Library causes the languages to drift apart from each other over time as the English source is revised — a maintenance-level "lost in translation" failure mode, not just a linguistic one.
2. A per-conversation, Staff-driven translation scales better and is easier to demonstrate as a PoC than a pre-generation pipeline that has to run for every narrative × every target language up front.
3. Fixing `NARRATIVES.md` to English specifically is the realistic call, precisely *because* the underlying FAO source data/documentation is itself in English — there's no reason to translate away from the one language everything is actually verified against, and doing so removes a source of instability rather than adding one.
4. Multilingual quality is capped by "whatever Staff's capability happens to be at the moment it's asked" regardless of design — Staff is inescapably acting as an interpreter here, so the design should lean into that rather than trying to pre-empt it.
5. This reframes `NARRATIVES.md` itself: it's not just a list of pre-built links, it's a **Library** in the Staccato architectural sense — a stable, single-source-of-truth content store that Staff (the interpreting role) draws from and adapts, mirroring the Staff/Library split the rest of the architecture already has. This is a genuinely new interpretation surfaced by this discussion, not something `staccato-spec` or this repo had previously named.
6. Pre-generating every language variant "just in case" is exactly the kind of needless upfront toil the hacker ethic's laziness virtue warns against — hfu's words: "NARRATIVES.md を単言語にするのは、hacker倫理における怠惰の高いレベルでの発揮だ。勤勉がはびこる余地を排除しなければならない" (keeping `NARRATIVES.md` monolingual is laziness exercised at a high level, in the good hacker-ethic sense — room for needless diligence has to be actively eliminated, not just left alone).

### D36 — Real production bug found and fixed: 5 live Côte d'Ivoire `-final.geojson` layers were in EPSG:3395, not WGS84
**Date**: 2026-09-05
**Status**: Fully resolved. Fixed, re-uploaded, confirmed correct on the origin server, and now also confirmed correct through the public `depot.optgeo.org` URLs themselves (re-checked directly: all 5 now serve `CRS84`/valid Côte d'Ivoire coordinates) — either `stars-cd` purged the edge cache or it self-healed on its own `max-age=14400` TTL; not distinguished, and not worth chasing further now that the actual visible result is confirmed correct.

**How this was found**: while gathering real data for a Côte d'Ivoire dairy narrative (a `NARRATIVES.md` in progress, see below), `hih-civ-dairy-final.geojson`'s coordinates turned out to be things like `(-578066, 1074111)` — not valid lon/lat by inspection alone (longitude must be in [-180,180]). The file's own `crs` member correctly declared `EPSG::3395` (World Mercator) — but that's the point of the bug: GeoJSON's RFC 7946 spec mandates WGS84 and deprecates the legacy `crs` member, and MapLibre GL JS (like virtually every modern GeoJSON consumer) ignores it entirely, treating raw coordinates as WGS84 lon/lat unconditionally. Checked all 5 live Côte d'Ivoire `-final.geojson` files (`cereal`, `fruits`, `vegetables`, `dairy`, `livestock`) — **all 5 were EPSG:3395**, all wired live into `docs/index.html` (lines 160-164) since D30. On the real public map, these 5 "FAO-selected site" layers were rendering at nonsensical locations (or failing to render at all), not the real Côte d'Ivoire sites.

Harmless no-op-plus-regrid for already-WGS84 sources.

### D32 — `#q=` shorthand added: a hand-typeable Map Intent hand-off for a prompt-only Staff (with real chukei/spiccato consultation)
**Date**: 2026-09-04
**Status**: `docs/map_intent.js`/`docs/story.js` changes built and verified in-browser (three-way regression: `#intent=`, `#story=`, `#q=` all confirmed working). `STAFF-PROMPT.md` rewrite and live-agent testing still to come (this session's approved plan, `.claude/plans/declarative-floating-wadler.md`).

**The corrected mental model**: hfu directly corrected an assumption this project had been carrying — "building Staff" does not mean standing up a backend service calling an LLM API. Staff's implementation IS the system prompt; Staff manifests inside whatever general-purpose AI chat agent has that prompt loaded (a Claude Project, a custom GPT, anything). No new server, no new API-calling code was ever needed. This matches ADR 0001's own "Faceless Cartographer" framing more literally than this project had previously realized.

**Real, substantive consultation with `dwg7/chukei`** (a working Japanese-language Staff-as-prompt deployment for GSI Hokkaido, via Japan's "Gennai" GenAI portal) — both by reading its and its Cartographer counterpart `spiccato`'s actual source directly (`/Users/hfu/Downloads/chukei`, `/Users/hfu/spiccato` — real local checkouts, not GitHub-API summaries) and via a live cross-session exchange with `chukei-24`. **The single most load-bearing finding**: chukei/spiccato's hand-off to their Cartographer is a plain, uncompressed, human-typeable URL fragment shorthand (`#q=req=...&lat=...`), not a compressed blob — because a chat portal with no code-execution capability means the LLM has to hand-type the final URL character-by-character, and an LLM cannot compute a real LZString/base64 encoding "in its head." This directly exposed a real gap in ferspas57: the only fragment-based hand-off path (`#intent=<LZString-compressed-YAML>`) is unusable by a genuinely tool-less Staff — only the verbose full-YAML paste-box was ever actually reachable by one.

**Built `#q=`**, ferspas57's own analogue (same key name as chukei/spiccato, deliberately — one consistent grammar across dwg7 projects), deliberately narrower than spiccato's own version since checked against what this Cartographer's code actually needs, not assumed: `#q=req=<id[|label],...>&lat=&lng=&zoom=&goal=&name=` — no `catalog=`/`type=` (one fixed catalog; `applyMapIntent()` doesn't route by catalog at all), no `opt=` (required/optional already flatten into one list with identical activation, no UI distinction exists to justify it), no `bbox=` (`parseMapIntent()` never stores `doc.area` at all — only `render_hints` drives the camera). `lat,lng` order (not `[lng,lat]`) matches how a Staff would say a coordinate in prose, reducing transposition risk — copied directly from spiccato's own stated reasoning.

**A second real bug found while testing, not just designing**: `readAndClearFragmentKey` (the shared ADR-0004 read-once-and-clear helper extracted from `story.js`'s `getStoryFromUrl()`/`map_intent.js`'s `#intent=` reader in this same change) originally split the whole hash on `&` and looked for a segment starting with `key=` — correct for `#intent=`/`#story=` (opaque LZString blobs with no literal `&` inside) but silently truncating `#q=`'s own value at its *first internal* `&`, since `#q=`'s value is itself a multi-param blob using `&` as an internal delimiter. Caught immediately by an actual in-browser test (`qRaw` came back as just `"req=gaez-aez33"`, silently dropping `lat=`/`lng=`/`zoom=`/`goal=`) — not by code review. Root-caused and fixed: the old multi-key "&"-joined design existed only to coexist with MapLibre's own `hash:"map"` reflection, which D22 already removed; with that gone, `#intent=`/`#story=`/`#q=` are never actually combined in one URL (each is a complete, standalone hand-off), so the fix is to treat the *whole* hash as one key's value rather than "&"-splitting it — simpler and correct, not just patched.

**Verified in-browser** (not just "the code looks right," per this project's own standing discipline): a three-way regression pass confirmed `#intent=` (LZString YAML), `#story=` (LZString JSON), and the new `#q=` all correctly parse, apply (checkbox activation, camera fly), and clear their fragment to empty — run together in one session against the actual current code, with a browser-caching gotcha (this session's browser-automation tooling was found to cache static `.js` files by exact URL independent of server-side changes — `fetch(..., {cache:"no-store"})` with a cache-busting query string was needed to actually exercise the edited files) worth remembering for whoever tests this next.

### D27c — Real bug found and fixed: NaN-NoData sources were silently miscast to a real score value, not masked
**Date**: 2026-09-04
**Status**: Fixed in `scripts/convert-hih.sh`; the one already-affected staged file (`hih-caf-cassava-score`) re-converted and verified. No live production archive affected (checked directly, see below).

**How this was found**: while gathering source resolutions for the shared fishfarm/access archive merge (D27's paused step), the DR Congo fishfarm-closed source COG turned out to declare its NoData as literal `nan` — not `-9999`, not `-3.4e38` like every file checked so far. That prompted checking what `scripts/convert-hih.sh`'s mask condition, `(A<=-9999)|(A>100)`, actually does with NaN input: **NaN comparisons are always `False` in numpy**, so neither half of that condition ever catches a NaN pixel — it falls through to the "keep as real data" branch, gets `numpy.round`ed (NaN stays NaN), and the final `.astype(numpy.uint8)` cast silently produces `0`, not 255. A NoData pixel becomes indistinguishable from a genuine, valid zero score — with no error, no exception, just a quiet `RuntimeWarning: invalid value encountered in cast` easy to read past.

**Checked whether this had already shipped**: yes for one already-completed file — `hih-caf-cassava-score`'s own source also declares NoData as `nan` (confirmed directly: `gdalinfo` shows `NoData Value=nan`), and its already-converted `_byte.tif` was still sitting in this session's scratchpad. Direct pixel comparison confirmed the bug was real in that specific staged output (not yet uploaded anywhere, per D27's own "staged, not deployed" note — caught before it could reach production). **No currently-live production archive is affected**: the original DR Congo fishfarm-closed conversion (done by hand in the original D7-D11 batch, before this script existed) was checked pixel-by-pixel against its own NaN source and found to correctly map 100% of NaN positions to byte 255 — whatever hand-run `gdal_calc.py` invocation was used originally evidently handled this correctly (very likely by relying on `gdal_calc.py`'s own default respect for an input band's registered NoData value, rather than an explicit numeric-threshold condition), even though this script's own simplified re-implementation of "the same idea" did not.

**Fix**: the mask condition now checks `numpy.isnan(A)` explicitly, and the "keep" branch replaces NaN with 0 (via an inner `numpy.where`) *before* rounding/clipping/casting, both catching the NaN case and eliminating the cast warning entirely (rather than just suppressing it) since the cast never sees a NaN input on either branch anymore.

**Re-verified**: `hih-caf-cassava-score` reconverted; direct pixel check confirms 100% of the source's NaN positions (55.7% of all pixels — a genuinely large fraction, not an edge case) now map to byte 255. `pmtiles verify` clean. CIV's five commodities were checked and confirmed **not** affected (their sources all declare NoData as `-3.4028235e+38`, which the original `<=-9999` condition already caught correctly) — no re-conversion needed for those.

**Why this is worth dwelling on**: this is exactly the class of silent-corruption risk this project's own established philosophy (D7/D8's resampling discipline, the "厳禁" stance on lossy encoding for classification data) exists to guard against — a plausible-looking, warning-only failure mode that produces a technically-valid-looking output (a byte value in the correct 0-100 range, not an obviously-wrong number) while actually corrupting the transparent/NoData signal into "this place scored exactly 0." Caught here because the file was re-inspected for an unrelated reason (resolution audit), not because anything visibly broke — worth remembering that a clean `pmtiles verify` and a plausible-looking tile do not by themselves prove correctness for this kind of masking logic.

### D22 — D21's ADR 0004 fix didn't actually work: MapLibre's `hash:"map"` was reinjecting the cleared payload; fixed by removing it, plus a second latent bug it exposed
**Date**: 2026-09-03
**Status**: Fixed and verified end-to-end (real shared story link → fresh receiving page → payload cleared and stays cleared through multi-step playback).

**What verifying D21's fix (rather than trusting it) found**: loading a real story-share URL fresh, the fragment was correctly cleared by `getStoryFromUrl()`'s new `history.replaceState` call — but reappeared in full immediately afterward, once `startStory()`'s first `flyTo()` fired a `moveend`. Root cause: MapLibre's own `hash: "map"` constructor option (added D11, for center/zoom URL convenience) captures the fragment's non-`map=` remainder at construction time and re-splices that cached copy back in on every map-driven hash update — so our synchronous clear was immediately undone by MapLibre's own next write, using a stale copy from *before* the clear. This is a stronger, actively-broken version of the ADR 0005 gap D21 flagged and deferred ("continuously reflects live map state... tracked as follow-up, not done in this pass") — it turns out that gap doesn't just violate ADR 0005's reflection-should-be-gated rule, it defeats ADR 0004's one-shot-clear guarantee too, for any sharing mechanism built on the fragment (both `story.js` and `map_intent.js`).

**Fix**: removed `hash: "map"` from the map constructor in `docs/index.html` entirely, rather than attempting to patch around its caching. This repo has no session-scoped `sharing_policy.url_share` toggle UI (the deferred ADR 0005 item), so "no continuous reflection at all" is the correct interim default for a faceless Cartographer per ADR 0005 — not a partial fix standing in for the real one. `story.js`'s own `flyTo`/`applyMapIntent`'s `flyTo` already drive the camera independently of any hash mechanism, so nothing depended on MapLibre's hash for camera restoration.

**A second, previously-latent bug this exposed**: with `hash:"map"` gone, a freshly-shared story/intent link's fragment is now just `#story=<payload>` (no leading `map=...&` from MapLibre to precede it) — and `getStoryFromUrl()`/`map_intent.js`'s reader both used a regex, `/(?:^|&)story=([^&]+)/`, whose `^` only matches "story=" at position 0 of the raw hash string, never realizing the string actually starts with a literal `#` character. So `"#story=X"` never matched at all — only the `"#map=...&story=X"` shape (accidentally guaranteed by the now-removed `hash:"map"`) ever worked. Fixed in both files by switching to a split-on-`&`/find-by-prefix approach that's agnostic to position and to the leading `#`; also fixed the mirror-image bug in `story.js`'s `setStoryInUrl()` (same regex pattern, same flaw, on the write side).

**Verified** (in-browser, via direct calls to the real functions rather than assumption): (1) a synthetic `#story=X&map=Y` hash — the old, accidentally-working shape — clears correctly and stays cleared through a manual `moveend`; (2) a synthetic `#story=X`-only hash (the new, realistic shape) — which silently failed to even parse under the pre-fix regex — now clears correctly too; (3) a full real `shareStory()` → fresh-load → `startStory()` round trip: fragment length drops from 10,424 chars to 0 immediately on read, and stays at 0 after the first step's `flyTo`/`moveend`, with the correct title/caption rendered from the decoded payload.

**Lesson for this repo's own working style, worth keeping**: D21 reported the ADR 0004 fix as done without exercising the *receiving* side of a real link — it happened to be right about the mechanism's legitimacy but wrong about whether the specific code satisfied it. The gap only surfaced because the receiving-side test was actually run end-to-end afterward, not because the earlier reasoning was re-checked on paper. Worth remembering next time a "should now be compliant" claim is made off of a single-direction (sending-side) test.

**Still owed, now updated**: the ADR 0005 gap D21 flagged is now resolved to its correct interim state (reflection off by default, no toggle exists yet) rather than left as "known broken" — a future session adding a session-scoped `sharing_policy.url_share`-gated "share current view" affordance should build it as a deliberate, policy-checked `location.hash` writer, not by re-adding MapLibre's built-in `hash` option, which this entry has now shown actively conflicts with ADR 0004 compliance. The narrative-extension ADR for `staccato-spec-19` (owed since D6/D12/D19/D21) is still not drafted.

### D21 — `staccato-spec`'s ADR 0001/0004/0005/0007 change the picture from D19: the URL-fragment mechanism is spec-legitimate, but was missing a required behavior
**Date**: 2026-09-03
**Status**: Real compliance bug found and fixed in `story.js`/`map_intent.js`. D19's framing of the fragment mechanism as merely "optional/lesser" needs correcting — it's a named, already-proposed pattern for exactly this deployment's shape, not an afterthought.

**What reading the actual ADRs (`0001`, `0004`, `0005`, `0007` — fetched directly from `UNopenGIS/staccato-spec`, not assumed) revealed, beyond `map-intent-vnext.md`/`staff-system-prompt.md` alone**:

- **ADR 0001 (Faceless Cartographer, Accepted)** is more specific than this session realized: its baseline endpoint model is literally `GET /` (a form) and **`POST /`** (submit Map Intent, render). This directly uses POST — the exact thing hfu wanted to avoid for this project. Resolving that apparent conflict: `hfu/faceless-cartographer` is a *separate*, server-backed reference implementation of that baseline, not this repo. ferspas57 is a static-only, no-backend deployment, which is a different profile than ADR 0001's baseline literally describes.
- **ADR 0004 (one-shot, cleared-on-load URL fragments) is exactly the missing justification for that different profile**, and it already exists, Proposed status, citing the same `hfu/faceless-cartographer` lineage: a Map Intent MAY be handed off via `#intent=<payload>`, satisfying the faceless baseline's URL/data-minimization guarantees, **provided the fragment is read at most once and cleared via `history.replaceState` before any rendering derived from it occurs** — so a URL copied after the map has rendered is indistinguishable from one with no fragment. This means D15/D19's whole "compress into a URL fragment" mechanism isn't a lesser, spec-tolerated workaround — it's a real, already-named pattern for precisely this no-backend deployment shape. D19's framing ("kept as the spec's explicitly-optional enhancement, not the required baseline") undersold it; the correction here is about how *legitimate* it is, not about demoting the plain-text/paste-box path, which remains correctly the required baseline per `map-intent-vnext.md`.
- **Real bug found from actually reading ADR 0004's requirement closely**: neither `story.js`'s `getStoryFromUrl()` nor `map_intent.js`'s URL-fragment reader cleared the fragment after reading it — a URL copied after D15/D20's demos rendered would still show the full compressed payload, violating ADR 0004's explicit requirement and reintroducing exactly the bookmarkable/persistent-URL-state risk the faceless baseline exists to prevent. **Fixed**: both now call `history.replaceState` to strip just the `story=`/`intent=` key (preserving MapLibre's own `map=` hash key, which is a separate, *not yet* spec-reconciled concern — see below) immediately after reading, before the story/intent is applied.
- **A related, NOT yet fixed gap, noted rather than rushed**: MapLibre's own `hash: "map"` option (used since D11 for center/zoom convenience) continuously reflects live map state into the URL unconditionally — which is exactly what **ADR 0005 (session-scoped fragment reflection)** says should default OFF unless an intent's `sharing_policy.url_share` is `true`, gated behind a human-controlled, session-scoped toggle. Current behavior is closer to ADR 0005's explicitly-rejected "Always-ON live reflection" alternative. Properly fixing this means replacing MapLibre's built-in `hash` option with a custom, policy-gated implementation — real work, not a one-line patch — tracked in `HANDOVER.md`, not done in this pass.
- **ADR 0007 (`required_styles`/`optional_styles`)**, while not immediately actionable for ferspas57, is worth knowing: the same production `stars.optgeo.org` Martin instance already serves complete curated MapLibre styles for other dwg7 projects (`hfu/kitavolca`-derived `vlcm`/`vbm`, via `GET /style/{style_id}`) — meaning if ferspas57 ever wants to publish a curated, pre-designed "product" (e.g. a finished GAEZ+HIH composite view) rather than raw layers, that mechanism already exists and is proven on the exact server this project uses.

**Still owed**: the multi-step narrative extension ADR for `staccato-spec-19` — none of 0001/0004/0005/0007 address the "sequence of camera states + captions" question (`render_hints` is still single-state only); this session's earlier plan to draft that ADR (D19) still stands, now with much better grounding in how the existing ADR set actually reasons about deviations (the append-new-ADR-rather-than-edit-existing pattern, real reference-implementation evidence requirement, explicit trade-off/alternatives-considered structure) to follow.

**Dynamic (mouseover) legend for AEZ33 — implemented, with a real MapLibre v5 gotcha found along the way**: hfu's framing, referencing `kitavolca`'s approach — show the one relevant legend entry near the cursor, not a static list of all 33 classes sitting on screen. Mechanism: since our PNG8 tiles are baked from FAO's own official colormap (D8), the actual rendered pixel color can be read back off the WebGL canvas and reverse-matched to a class.
- First attempt used `preserveDrawingBuffer: true` on the `Map` constructor (the documented way to keep a WebGL buffer readable outside the render loop) — **this option is silently ignored in MapLibre GL JS 5.24.0**: confirmed via `gl.getContextAttributes()` on a freshly-created, otherwise-empty map that the resulting context always reports `preserveDrawingBuffer: false` regardless of the constructor option. Not a config mistake on this session's part — reproduced in isolation.
- Working fix: don't rely on the buffer persisting. On `mousemove`, call `map.triggerRepaint()` and read pixels *synchronously inside* the `render` event it triggers (`map.once("render", ...)`) — the frame is guaranteed valid at that exact moment, before the browser's next composite/clear. This is the same pattern well-known raster-picking implementations use for exactly this reason.
- Second gotcha: exact color matching (which works fine for flat-Mercator raster rendering with `raster-resampling: nearest`) isn't reliable once **globe projection** is active — globe reprojects the flat tile texture onto a sphere mesh, and that resampling doesn't obviously respect the raster-resampling paint property the same way, so baked palette colors can arrive slightly blended. Switched to nearest-color matching (smallest squared RGB distance, rejecting anything not reasonably close) instead of an exact lookup table — confirmed correct in testing (hovering the Congo basin correctly reported "AEZ33 — 26: Land with severe soil/terrain limitations", matching D13's own finding).
- Scoped to `gaez-aez33` only for now (its 33-class legend is verified against FAO's primary GAEZ v4 guide, D13); AEZ57's 57-class legend text hasn't been sourced yet.

### D10 — HIH color/format decisions: hidden -9999 sentinel in Score layers, and FinalLocation moves from raster to vector
**Date**: 2026-09-03
**Status**: Decided (hfu confirmed the process/direction; the FinalLocation raster→vector call itself is this session's technical judgment, made explicitly to be checked, not assumed final).

**Context**: per hfu's explicit instruction, the HIH color/encoding question was investigated *before* running any conversion (unlike GAEZ, where D7/D8's color problems were found and fixed after a first bad build). Downloaded and inspected real DR Congo COGs directly (`COD-LOCATIONSCORE-MAIZE`, `COD-FINALLOCATION-MAIZE`, `COD-LOCATIONSCORE-CASSAVA`) rather than inferring from STAC metadata alone, since — unlike GAEZ's `AEZ33`, whose official colormap was fully embedded in `renders.data.colormap` — HIH's STAC `renders` property only carries a `colormap_name` reference with no embedded values, meaning the actual palette (if any) lives only inside FAO's own WMTS renderer, not in data this session can read directly.

**Finding 1 — Score layers (`LOCATIONSCORE`/`SCORE`, Float32) carry a hidden second nodata sentinel**: `COD-LOCATIONSCORE-MAIZE`'s declared `NoData` is the standard float32 sentinel (`-3.4028235e+38`), but a histogram revealed **8,204,781 pixels — nearly half of all "valid" pixels — actually hold the literal value `-9999`**, an undeclared secondary "excluded area" flag GDAL doesn't recognize as nodata. This single value was dragging the naive statistics wildly negative (`Mean=-4717`) and would have wrecked any naive min/max color stretch. Genuine score values cluster in roughly 0–76 (this commodity/country's actual range). The identical 8,204,781-pixel count reappears in `COD-FINALLOCATION-MAIZE`'s own histogram, confirming it's one shared "outside the studied area" mask reused across a country's whole HIH layer family, not a per-file quirk.
- **Decision**: treat `-9999` (and the declared float32-nodata) both as transparent/excluded when building the color table — not just the declared NoData value alone.
- **Decision**: use a **fixed universal domain, 0–100**, for every Score layer's color ramp, not a per-file auto-stretched min/max — so different commodities and countries stay visually comparable (a weak-suitability country shouldn't look "hot" just because its own file has a lower local maximum). A generic, colorblind-safe sequential ramp (not a diverging one — suitability is a one-directional concept) will be used, deliberately *not* claimed as FAO-official (unlike GAEZ's real colormap, none exists here) — this is this repo's own reasonable convention for continuous suitability data, consistent with common GIS practice for this data type. Mechanically, scores will be rounded/binned to integer steps and baked into a ~101-entry GDAL color table, reusing the exact same PNG8-indexed pipeline validated in D8 rather than introducing a second encoding path for continuous vs. categorical data.

**Finding 2 — FinalLocation layers (Int16) are extremely sparse binary site-selection flags, not a raster-shaped dataset**: `COD-FINALLOCATION-MAIZE` has a clean, single, standard `NoData=-32768`, but only **417 pixels out of ~18.1 million hold the "selected site" value (1)** — everything else is either the shared `-9999` exclusion mask or genuine nodata. This is a single-digit-percentage-of-a-percent sparse point pattern, not a raster surface.
- **Decision (this session's call, explicitly flagged for hfu to override)**: convert FinalLocation layers to **vector point features (GeoJSON)**, not raster/PMTiles, reversing D9's assumption that all 14 DR Congo commodity files (`-score` and `-final` pairs) would be built the same way. Reasoning: nearest-neighbor overview/pyramid downsampling (mandatory for any categorical/sparse raster per D8) can and likely would make a 417-pixel feature vanish entirely at most zoom levels a real map would actually be viewed at — the raster pipeline that works well for Score's continuous surface is the wrong tool for a handful of point-like selected sites. A point feature with attributes (commodity, country, score-at-site) is also a more directly useful UI primitive for "here is where FAO's analysis says to build this" than a nearly-invisible raster pixel cluster.
- This changes D9's file list in kind, not in name: the seven `hih-cod-{commodity}-final` names stay as planned, but as GeoJSON/vector sources rather than PMTiles raster sources. `hih-cod-{commodity}-score` stays raster PMTiles as originally planned.

**Color encoding — approved**: D7's first colored build used `gdaldem color-relief` to bake FAO's official `AEZ33` colormap (found in the STAC item's `renders.data.colormap` property — the actual authoritative source, not `classification:classes`, which is empty for GAEZ-V5 unlike ESA WorldCover) into a real 4-band RGBA GeoTIFF. That produced a working but bloated 184MB PMTiles (vs. the uncolored 34MB baseline) — 4 bytes/pixel instead of 1, and full RGBA PNG compresses far worse than an indexed image for a ~33-color categorical map. Fix: attach the same official colormap as a genuine GDAL **color table** (PCT) to the original single-band class-code raster instead — via a hand-edited VRT (`<ColorTable>` with per-value `<Entry c1..c4>` entries, transparent for nodata=255) — so `gdal_translate -of MBTILES` emits real indexed-color PNG (PNG color type 3), keeping pixels at 1 byte each.
- First attempt at this still came out oversized (70.8MB) — root cause found: `-co RESAMPLING=NEAREST` had been added to `gdaladdo`'s overview-pyramid step but was **missing from the base `gdal_translate -of MBTILES` reprojection step itself**, letting GDAL's default resampling interpolate index values across class boundaries during the EPSG:4326→3857 warp — inventing meaningless intermediate class codes at every edge, which also happens to be exactly the kind of corruption categorical data must never undergo. Real lesson: **nearest-neighbor must be forced at every resampling step in the pipeline, not just the overview-building step** — the base warp has its own independent default.
- With that fixed: PNG8/indexed came out **36.5MB**, matching the uncolored baseline closely. A same-fix comparison against `TILE_FORMAT=WEBP, QUALITY=100` produced **92.2MB** — worse, and GDAL's MBTiles/WEBP writer has no true lossless option (`QUALITY` is a lossy-only knob), which is disqualifying on its own for categorical data regardless of size (hfu, emphatic: lossy compression on class-coded data is 厳禁 — strictly forbidden, corrupts values at boundaries). **Decision, approved by hfu: PNG8/indexed color**, not WebP, for all categorical FERSPAS layers (GAEZ and HIH alike) — smaller, and correct by construction rather than by trusting an encoder setting.

**File naming — flat, not nested (corrects D7)**: this session's first proposal (`ferspas57/aez33-1km.pmtiles`, one subdirectory per project) was rejected — Martin's own conventions don't practically support directory nesting for registered tile sources, and hfu characterized Martin's culture as closer to Unix/DOS: short, flat, unceremonious names. Landed on: **short, flat, collection-ID-derived names with no path nesting** — e.g. `aez33`, `aez57` for the GAEZ layers (dropping the `ferspas57-`/`gaez-v5-` prefixes entirely, since flat short names are the house style, not because provenance doesn't matter — provenance lives in TileJSON `attribution`/metadata instead, per `cafebabe`'s D6 finding that this costs nothing extra in MapLibre).

**HIH's cross-country merge strategy**: hfu's stated ideal is that "the same kind of layer" should be one PMTiles regardless of country — Congo or Bhutan, if it's conceptually the same thing, it's the same layer. Checked this against the actual naming/content of all HIH collections across the six D6 target countries (DR Congo, Bhutan, Côte d'Ivoire, Central African Republic, Cameroon, Republic of Congo) rather than assuming it holds:
- **Fish-farming siting (closed/open/extensive, +photovoltaic variant) merges cleanly** across 5 of 6 countries (all but land-locked, non-fish-farming Bhutan) — the methodology and sub-types are genuinely the same everywhere, modulo cosmetic naming-string differences (`FISH-` vs `FISHFARM-`, `EXTNSV` vs `EXTENSV`). Proposed flat names: `hih-fishfarm-closed`, `hih-fishfarm-open`, `hih-fishfarm-extensive`, `hih-fishfarm-closedpv`.
- **Weighted urban accessibility merges across 4 of 6** (DR Congo, Côte d'Ivoire, Central African Republic, Republic of Congo) once a real naming inconsistency is normalized (`WGTH` vs `WGHT` — a plain typo divergence between countries, not a semantic difference). Proposed: `hih-access-urban`. Port accessibility (DR Congo + Central African Republic only) and city accessibility (Bhutan only) are separate, much smaller-footprint layers.
- **Crop-storage siting mostly does not merge** — the six countries studied genuinely different commodities (DR Congo: cassava/cocoa/coffee/maize/palm-oil/wheat; Bhutan: rice/citrus/asparagus/cereal/tropical-fruit/vegetables; Côte d'Ivoire: broad cereal/fruit/vegetable buckets; Central African Republic: cassava only, abbreviated `CSSV`; Cameroon and Republic of Congo have none at all in this theme). There is essentially no cross-country overlap in which commodity was studied, so forcing a merge would misrepresent the data rather than simplify it. Proposed: keep these per-country (e.g. `hih-cod-maize`, `hih-btn-rice`), not merged, at least until/unless FAO's own HIH coverage grows enough commodity overlap between countries to justify it. Dairy-processing and slaughterhouse siting are similarly thin (2–3 countries each, with their own naming inconsistencies — e.g. Bhutan's own `LOCATIONSCORE-DIARY`, a typo for `DAIRY`, inside its own data) and are being left per-country for the same reason.

**Not yet confirmed**: the HIH merge/naming proposal above reflects this session's analysis of real data, but — unlike the PNG8 color-encoding decision, which hfu explicitly approved — hasn't yet received the same explicit sign-off from hfu as a final naming scheme.

### D7 — Tentative: host the GAEZ PMTiles on `stars.optgeo.org` (Martin-served), not client-side `pmtiles.js`
**Date**: 2026-09-03
**Status**: Tentative (hfu's own word: 仮決定) — a working direction, not a closing of D2's broader tile-serving-architecture question, and nothing has actually been deployed to `stars` yet.

**What**: First real end-to-end technical validation of D3/D6's option (C), run locally against the actual GAEZ-V5 `AEZ33-1KM` COG (33.2MB):

2. `pmtiles convert` (the same Go CLI `mapterhorn-japan-bridge` recommended, D2) turns that MBTiles into a PMTiles archive: **34,254,666 bytes (34.25MB)** for `AEZ33-1KM`, `pmtiles verify` clean, z0–z7, 21,845 addressed tiles. `AEZ57`'s source COG is a near-identical 32.6MB, so expect a similarly-sized archive — not yet converted as of this writing.

4. 5. **Decision**: given (a) the archive size (~34MB, comfortably inside "tens of MB," hfu's own threshold for this call) and (b) finding (4) above — a live, first-hand demonstration that client-side `pmtiles.js` is the more fragile path (Range-request-dependent, breaks against naive servers) versus a real server (Martin on `stars.optgeo.org`) doing the same PMTiles-reading job server-side and handing the client a plain tile/TileJSON endpoint — hfu's tentative call is to **host this PMTiles archive on `stars.optgeo.org` via Martin, not as a client-fetched static `.pmtiles` file with `pmtiles.js`**. hfu's stated reasoning: attaching `pmtiles.js` to the site "isn't elegant" (エレガントではない) — this session's own accidental reproduction of `pmtiles.js`'s server-requirements fragility is a concrete technical point in favor of that instinct, not just an aesthetic preference.

**Still not decided**: this is scoped to the small, self-generated GAEZ PMTiles specifically — it does not resolve D2's broader question (which was largely about much larger/raw-COG scenarios) or commit HIH's data to the same path yet. Nothing has actually been uploaded to `stars.optgeo.org` — `stars-fd` asked in D2 that any concrete step be run past hfu first, and separately, actually placing something on shared infrastructure is itself a to-be-had conversation, not a unilateral action, per D6's own reasoning for staying local-only until it is.

### D4 — Value proposition reframed as an open, freely-reimplementable analog to FAO's own AIDA, scoped to a GAEZ×HIH cross-narrative
**Date**: 2026-09-03
**Status**: Direction set; the underlying technical/content sizing this depends on is being gathered next (see "Still needed").

**What HIH actually contains, in full** (131 collections surveyed by ID + title — **note**: collection *counts* below were later found to overstate actual usable content; see D5's item-level audit, which found 39 of these 131 to be empty stubs with zero STAC items): coverage spans 17 countries, extremely unevenly by collection count — DR Congo (21 collections), Bhutan (17), Côte d'Ivoire (15), Djibouti (13), Central African Republic/Eritrea/Ghana (11 each) *appeared* to have FAO's full multi-theme Hand-in-Hand siting toolkit by collection count alone; Benin, Cabo Verde, Belize, Colombia, Cuba, Iraq have only one or a few one-off layers. Five recurring themes: crop storage/processing siting (52 collections, commodity-specific — cereal, cassava, cocoa, coffee, palm oil, maize, wheat, beans, fruit, vegetables), fish-farming siting (32, split by system type — closed/open/non-intensive — and species — African Catfish, Nile Tilapia — with a photovoltaic-power variant), accessibility (19, travel-time-cost to cities/ports plus demand-weighted composites), dairy-processing siting (14), slaughterhouse siting (14). Almost every theme comes as a **Score** (continuous suitability raster) paired with a **Final Location** (the derived/selected actual site) — i.e. HIH is not a pile of miscellaneous maps but a consistent, repeated siting-decision methodology applied per country per commodity. All raster (not vector, as one might expect for "site" data), and — unlike GAEZ — clipped to national/sub-national extent, so individual files are tiny (measured: 0.37MB–7.3MB per collection sampled).

**Two observations feeding the reframe**:
- hfu, from `dwg7/chukei` experience: generative AI is already known to be good at exactly this task — inferring thematic classification from cryptic layer-name codes (chukei's own domain-vocabulary work is the precedent). HIH's `{COUNTRY}-{STAGE}-{COMMODITY}` naming convention (e.g. `COD-FINALLOCATION-MAIZE`) is squarely this kind of problem, which is why an AI-narrative layer over it is plausible, not speculative.
- Checked directly (WebSearch, 2026-09-03) whether FAO has already built the "AI narrates a path through buried geospatial data" idea this session arrived at for HIH: **yes, largely.** FAO's own **AIDA** (Agro-Informatics Digital Assistant, `aida.fao.org`) explicitly frames its mission as changing the starting point "from 'Where is the data?' to 'What do I need to know?'" — the same value proposition, in FAO's own words, connecting statistics/water/forests/animal-health/prices/**geospatial products**/advisory knowledge through one natural-language entry point that can return interactive maps. Depth of actual geospatial-layer narrative guidance (e.g. whether it does anything like walking a user through HIH's fragmented per-country siting toolkit specifically) isn't documented publicly. Per DWG5's `yuiseki` in `UNopenGIS/7#932` (June 2026), AIDA is **closed-source and closed-system** with almost no public technical documentation.

**Decision**: given AIDA already exists and stakes out very similar territory, ferspas57's honest differentiator is not "an idea FAO hasn't had" — it's building an **open, freely-reimplementable analog**, in the spirit of the kind of open-alternative-to-closed-system thinking hfu associated with something `yuiseki` has discussed on a radio/podcast appearance (referenced only in spirit here, not by specific content, since this session hasn't verified that source directly). Concretely, scoped narrowly rather than attempting to rival AIDA's full breadth:
- **GAEZ interpretation assistance**: AEZ33/AEZ57's classification codes are opaque without domain expertise — a narrative layer that turns "you clicked Zone 14" into a plain-language explanation of what that zone means agronomically is a real, self-contained piece of value, independent of HIH.
- **A GAEZ×HIH cross-collection narrative**: GAEZ answers "why is this place suited to X"; HIH answers "where specifically to build Y here." Weaving the two into one place-based story (e.g. "this part of DR Congo's agro-ecological zone suits cassava; here's where FAO's Hand-in-Hand analysis found the best cassava-storage site") is a cross-collection synthesis that showcases Staccato's actual architectural thesis — unifying heterogeneous catalog content into one experience — rather than a single dataset's UX, and isn't something a single-dataset viewer (or, as far as documented, AIDA) is confirmed to already do.
- This AIDA finding is DWG5-relevant and should be routed back to `UNopenGIS/7#932` per `CLAUDE.md`'s knowledge-flow-split guidance, independent of what ferspas57 does with it.

**Still needed before any technical build**: a detailed accounting — count, total size, and per-collection license — of the actual source data this hypothesis depends on: GAEZ-V5's shortlisted layers (D3: `AEZ33-1KM`, `AEZ57`, plus `HWSDV201`/`SLOPE-MED`/`LR-IRR` if still in play) and **all 131 HIH collections** (not just the samples characterized above). This is the next concrete task, requested by hfu explicitly before any conversion prototyping begins.

### D3 — "Good part" content shortlist: GAEZ-V5's global layers + HIH; WAPOR-3 and ESA WorldCover set aside for now
**Date**: 2026-09-03
**Status**: Shortlist fixed; final pick(s) to convert first still to be narrowed from it.

**What**: After surveying and sizing several candidate families from FERSPAS's 1282-collection catalog (see `HANDOVER.md` and D2), hfu set the working shortlist for what ferspas57 should actually convert and demonstrate:

- **GAEZ-V5**'s global ~1km (30 arc-second) thematic layers — `AEZ33-1KM` and `AEZ57` (Agro-Ecological Zones classification, 33/57 classes), `HWSDV201` (Harmonized World Soil Database), `SLOPE-MED`, `LR-IRR` (irrigable land resources), `ELEV-ALOS-30M`, and the rest of the ~108-collection family. Measured sizes range 28MB (`HWSDV201`) to 521MB (`ELEV-ALOS-30M`), with the flagship classification layers (`AEZ33-1KM`, `AEZ57`) at ~33MB each — a genuinely workable range for a real COG/PMTiles technical exercise, unlike ESA WorldCover's 182GB.
- **HIH** (the Hand-in-Hand initiative) — despite, and in part *because of*, its ~131 collections being fragmented into narrow, country×sector-specific site-suitability scoring layers (e.g. closed-pond fish-farming viability scores per African country: `CAF-FISHFARM-SCORE-CLOSEDPV`, `CMR-FISHFARM-SCORE-CLOSEDPV`, etc.) — see the reasoning below for why fragmentation argues *for* inclusion here, not against it.

Set aside for now (not eliminated, just off the active shortlist):
- **WAPOR-3** — a genuine FAO flagship (WaPOR water-productivity program) and reasonably sized at its L1/L2 continental tier, but judged "too specialized" (専門的すぎる) a subject to be a good first demonstrative target for a general audience.
- **ESA WorldCover** — this session's earlier top pick, now understood as the wrong choice: it is commodity data, already broadly available via AWS Open Data, Copernicus, and Element84 Earth Search independent of FERSPAS entirely. Converting it via FERSPAS wouldn't showcase anything distinctive to FAO or this collaboration.

**Why**: Three criteria converged, refined over the course of this investigation (hfu, verbatim in spirit): *"コンテンツとして魅力的で、データが大きすぎず小さすぎず、技術実証にちょうど良いのがgood partの定義"* (content that's genuinely appealing, data that's neither too big nor too small, technically well-suited to a proof of concept):

1. **Non-commodity, flagship content** — rules out ESA WorldCover; GAEZ (FAO+IIASA, running since the 1980s) and HIH (FAO's cross-cutting 2019 flagship initiative, its own dedicated geospatial platform) both clear this bar.
2. **Size in the workable middle** — ruled out both extremes found during this investigation: GAEZ's own `AEZ33` at native 0.5° resolution (733KB, too coarse/trivial to be a meaningful technical test) and ESA WorldCover (182GB, requiring special-case zoom-capping and infrastructure planning just to attempt). GAEZ's 1km family sits comfortably in between.
3. **A reframing of "handling ease" itself, prompted by hfu**: HIH's fragmentation was initially read (by this session) as a liability weighing against including it — 131 narrow layers are harder to present as one coherent thing than GAEZ's ~108 clean global variables. hfu inverted this reasoning: Staccato's whole premise, per `staccato-spec`, is to move *away* from being another catalog site or geoportal (脱カタログサイト、脱ジオポータル) — and a geoportal's defining failure mode is exactly that fragmented, narrow data gets buried in endless drill-down and never surfaces. HIH's fragmentation is therefore not a reason to exclude it; it is the ideal test case for whether ferspas57's actual differentiator — an AI-generated narrative that visually guides a user to the one specific buried layer they need, rather than a static catalog listing — works in practice. Converting only the easy, already-coherent case (GAEZ) would prove the tile-serving pipeline but not Staccato's actual value proposition. Converting only HIH, conversely, would risk having no clean technical baseline to build the harder UX against. Hence both are on the shortlist together, not as alternatives.

**Technical note**: for GAEZ-V5's global grid family, `mapterhorn-japan-bridge`'s native-leaf-tiles-then-separate-downsampled-pyramid technique (from its Japan DEM PMTiles work — see D2) was flagged by hfu as directly transferable, if GAEZ's various layers need to be presented as one seamless, consistently-tiled family rather than ~108 independently-built archives.

**Within-GAEZ-V5 narrowing (hfu, same day)**: of the candidate layers sized above, the Agro-Ecological Zones classification itself (`AEZ33-1KM` / `AEZ57`) is judged the "catchiest" (キャッチー) — more immediately legible and compelling than terrain or soil layers from the same family. `ELEV-ALOS-30M` (elevation) is specifically deprioritized for a different reason than the others: it would directly overlap (モロ被り) with `mapterhorn-japan-bridge`'s own existing scope (DEM/terrain PMTiles), so pursuing it here would duplicate a sibling dwg7 project's work rather than add something distinct. `HWSDV201` (soil) and `SLOPE-MED` remain on the table but are, so far, less compelling as the lead choice than the AEZ classification layers.

**Still open**: the final narrowing from {GAEZ-V5's AEZ33-1KM/AEZ57 (leading), HWSDV201, SLOPE-MED, LR-IRR; HIH} to whichever collection(s) actually get converted and demoed first; the HIH "AI narrative + visual guidance" UX is a stated direction here, not yet designed in any concrete form; D2's tile-serving architecture question (COG-direct vs. mirrored-COG vs. self-hosted PMTiles vs. FAO's WMTS wrapper) remains independently unresolved and will need an answer for whichever content ends up chosen here.

### D2 — Tile-serving architecture for FERSPAS raster collections: options surveyed, not yet decided
**Date**: 2026-09-03
**Status**: Open. Investigation and option-framing only — no option has been chosen.

**What we found by surveying the live catalog** (paged all 1282 collections via `https://data.review.fao.org/geospatial/search/stac/collections`):

- No orthophoto/aerial-imagery collection exists anywhere in the current 1282. The Niedersachsen DOP dataset hfu noted in `UNopenGIS/7#932`'s June 2026 comment (external data, CC-BY-4.0, provided by Germany's Niedersachsen state survey office LGLN, not FAO) was present in FERSPAS's catalog then but is **confirmed absent now** — removed at some point between June and September 2026, not merely renamed or missed by keyword search.
- Across all 33 top-level `fao-gismgr:*` sub-catalogs (sampled one representative item per prefix), asset structure is strikingly uniform: every item has a `data` asset (Cloud-Optimized GeoTIFF) plus `preview`/`thumbnail` assets served through a single FAO-run WMTS endpoint, `https://data.apps.fao.org/map/wmts/wmts`. No vector assets were found anywhere in the sample. This means FERSPAS's practical heterogeneity (as STAC-the-spec allows) is much lower than the STAC-in-general case — the catalog appears to be generated by one internal FAO GISMGR pipeline that normalizes everything to this same shape.
- That WMTS endpoint (self-identified in its `GetCapabilities` response as **"FAO WMTS WRAPPER"**, provider **FAO CSI**, contact **Mohamed Megahed** — the same team behind the June 2026 DWG5 presentation) serves every sampled layer through the standard `GoogleMapsCompatible` (Web Mercator, 256px, z0–z24) tile grid — i.e. it is already a de facto XYZ tile server for the whole catalog, confirmed working (`200 image/png`) against layers from `ESA`, `CRTB`, `GAEZ-V5`, `GLOSIS`, `HIH`, and `WAPOR-3`.
- Measured performance of that WMTS wrapper (ESA WorldCover 2020, `fao-gismgr:ESA:raster:maps:WC2020`): 200ms–4s per tile depending on zoom, one transient 503 observed near native-resolution zoom (not reproducible on retry), and — critically — `cf-cache-status: DYNAMIC` on every request including immediate repeats, meaning Cloudflare is not edge-caching these tiles at all despite a `Cache-Control: public, max-age=3600` header. Every tile request reaches FAO's live App Engine backend.
- The underlying COG itself (`gs://fao-gismgr-esa-data/DATA/ESA/MAP/ESA.WC2020.tif`, 195,668,306,548 bytes ≈ 182GB, global, ~9.28m/px native resolution) is a genuinely well-formed Cloud-Optimized GeoTIFF: 256×256 internal tiling, LZW compression, and a full 15-level internal overview pyramid (down to 132×66px). `storage.googleapis.com` correctly serves HTTP range requests (`206 Partial Content`, `Accept-Ranges: bytes`). **However, the bucket has no CORS configuration** (`access-control-allow-origin` absent from every response tested) — so a browser-side MapLibre COG reader cannot range-read it directly today, even though the file itself is structurally ready for that access pattern.

**Options on the table** (none selected yet):

- **(A) Direct client-side COG range access against FAO's own GCS bucket.** Best long-term outcome — no duplication, no extra infrastructure, matches Staccato's "reference, don't copy" philosophy most purely. Blocked today solely by the missing CORS header, which is FAO's to fix, not ours.
- **(B) Mirror the raw COG (unconverted) onto our own storage with CORS enabled**, e.g. GitHub or Source Cooperative — a temporary stand-in we'd disclose to FAO and retire once they enable CORS themselves. Not pursued further (option C was chosen instead — see D7 onward), so not elaborated here beyond the two concerns that mattered at the time: the mirror's own CDN might not even outperform GCS+Cloudflare, and mirroring FAO's data onto third-party infrastructure without their buy-in needs to be proposed transparently, not done silently, per this repo's "Positive intent" stance.
- **(C) Convert to our own zoom-capped PMTiles and host statically**, mirroring `layers-martin`'s static-hosting pattern but adding an actual conversion step (since, unlike GSI's source, FERSPAS's source is COG, not already-tiled). Full performance and hosting control; smallest diplomatic footprint since it's a clearly-derived, attributed display product rather than a raw-data copy; but full-native-resolution global PMTiles is infeasible for something the size of ESA WorldCover (182GB) — would need a deliberately capped max zoom (and possibly per-collection sizing work) to be practical.
- **(D) Consume FAO's existing WMTS wrapper directly, live.** Zero engineering cost, works today, but the measured latency (up to several seconds/tile) and complete absence of edge caching make it unsuitable as a production path — and routing real end-user traffic through it risks being a real burden on FAO CSI's own infrastructure, which cuts against this repo's reciprocity framing. Reasonable only as a low-volume prototyping/demo path, not a shipped architecture.

**Why this is being recorded now, unresolved**: hfu's framing is that this design reasoning — done logically, fairly, and tastefully — may itself be a piece of value this repo delivers, independent of which option is ultimately chosen; possibly even shareable back to FAO CSI as constructive feedback (the CORS gap in particular is something fixing would benefit the whole ecosystem, not just this repo). Recording the option space and evidence now, before forcing a premature decision, keeps that reasoning legible for whoever continues it.

**Two clarifications from hfu on 2026-09-03, refining but not resolving the above**:
- On option (B)'s "duplication" question: whether a mirror is *legally* permitted by FERSPAS's license is a separate axis from whether making one *without telling FAO* is the right thing to do. hfu's framing: doing it silently would be legally fine but relationally 水臭い (distant/standoffish — the kind of move that quietly erodes trust between collaborators) given this repo's stated reciprocity stance. If a mirror is ever built, it should be proposed to FAO transparently, not simply shipped.
- (B) and (C) are confirmed as the two main contenders. But hfu explicitly named keeping (A) and (D) "in view" rather than discarding them — i.e. staying ready to adopt (A) the moment FAO fixes CORS, and treating (D) as a legitimate (if limited) fallback rather than a non-option — as itself characteristic of dwg7's way of working: holding the full option space in mind rather than collapsing to a single path prematurely.

hfu also decided (B) and (C) both warrant actual hands-on prototyping, as tests of two different technologies rather than a pick-one call: (B) tests the current state of client-side COG-in-MapLibre reading technology; (C) tests the practical feasibility of dwg7's static/distributed-hosting vision applied to a genuine COG-sourced (not already-tiled) dataset. Two peer sessions were consulted for this:

**`stars-fd` on `stars.optgeo.org`** (asked 2026-09-03 what the platform is and whether it fits option B): it is hfu's personal Raspberry Pi (aarch64, Debian 13) running Martin, config-of-record in `hfu/stars` on GitHub with `stars-fd` as PR gatekeeper, exposed via a Cloudflare named tunnel as `stars.optgeo.org` (tiles/styles, Martin) and `depot.optgeo.org` (raw file browsing, Caddy, already `Access-Control-Allow-Origin: *`). Findings directly relevant to D2:
  - Martin's COG support is an opt-in `unstable-cog` Cargo feature **not present in the current production build (v1.14.0)** — so Martin-as-COG-tile-source is not available today regardless of hosting choice.
  - **Critical, previously-unknown risk for option (B)**: Cloudflare's proxy in front of `depot.optgeo.org` silently drops `Range` requests above some threshold between 190GB and 424GB, returning `200` (whole file) instead of `206`. Verified directly against origin (fine at 424GB) vs. through the public Cloudflare-fronted URL (76KB→206 OK, 190GB→206 OK, 424GB→200/Range ignored). A browser attempting to range-read a COG above that threshold through this specific host would try to download the whole file instead — unusable for datasets in that size class (ESA WorldCover's 182GB is close to, but apparently under, the danger zone; would need re-verification specifically, not assumed safe by proximity alone).
  - Option (C) is *not* subject to this problem: Martin does the range-reading server-side and returns normal tile responses to the client, regardless of source file size. Already proven at this kind of scale — `stars.optgeo.org` currently serves 168–198GB of Overture Maps data this way (as a remote PMTiles source, no local copy).
  - Capacity: 397GB free of 1.8TB on the host filesystem as of this check (fluctuates).
  - `stars-fd`'s own assessment: for a large (100GB+) permanent COG mirror, a purpose-built platform (e.g. Source Cooperative, S3-based, designed around CORS+Range) is more straightforward than a single Raspberry Pi with the Cloudflare quirk above; for small-to-medium (tens of MB–a few GB) PMTiles, `stars.optgeo.org` is already a proven, comfortable fit (cites the Vientiane zoning-data project). It explicitly asked that any concrete next step be run past hfu first, since the host is shared infrastructure across several dwg7 projects.

**`mapterhorn-japan-bridge/japan-geotiff-dem`** (asked 2026-09-03 for its GeoTIFF→PMTiles conversion know-how, for option C — it has built a ~314GB clustered PMTiles archive from national-scale GSI elevation DEMs at 1m/5m/10m). Its data is continuous (elevation), ours would be discrete (classification), so not everything transfers, but the operational lessons are directly usable:
  - Tooling: GDAL/rasterio (Python) for reprojection/aggregation, Go `pmtiles` CLI (`cluster`/`merge`/`verify`/`show`) for archive assembly, Python `pmtiles` library for bulk merges. No single-pass `gdal2tiles`-style descent.
  - Architecture lesson (conditional): if source resolution/coverage varies across the collection, build native-resolution leaf tiles first, then a *separate* downsampled-pyramid pass reading from those leaves — not relevant if a given FERSPAS collection is uniform-resolution throughout, but worth checking per collection before assuming a simple top-down build works.
  - Infra gotchas worth pre-empting rather than rediscovering: `go-pmtiles` respects `TMPDIR` but SSH sessions often carry a stale one that silently wins over `setdefault()` — force-override and confirm with `df` (cost them a corrupted 310GB archive once); always run `pmtiles verify` after cluster/merge (cheap, catches corruption `show` misses); `rsync` without `--whole-file` balloons memory doing delta-checksums against any pre-existing partial file at the destination; never trust a bare `glob()` to confirm a merge input is complete — use a per-region completion manifest instead (a naive glob once shipped them a silent ~25%-of-country gap); keep leaf-tile and pyramid-tile output in visibly distinct namespaces (a naming collision once cost them 3,344 tiles to a cleanup-script bug).
  - **For discrete classification data specifically** (directly relevant to something like ESA WorldCover's 11 land-cover classes): skip terrarium-style RGB float-packing (that's an elevation-only trick); prefer single-band tiles with the raw class code as the pixel value, recolored client-side via a MapLibre `raster-color`/match expression against the STAC item's `classification:classes` legend — keeps tiles smaller, keeps raw codes queryable, and allows restyling without regenerating tiles. Baking colors into RGB at generation time is the simpler-client alternative but forecloses both of those. Always use **lossless** WebP for class-code data — lossy compression blends/corrupts values at class boundaries. Expect favorable compression versus elevation-tile experience, since large uniform regions (ocean, forest blocks) collapse very well under lossless WebP run-length-style encoding.
  - **A real constraint to design around**: PMTiles/TileJSON support only one global `maxzoom` per archive — there is no per-region maxzoom anywhere in the stack. If parts of a collection only have genuine native detail to a shallower zoom than others, the archive will over-declare depth for those regions and deep-zoom requests there will 204. Mapterhorn is mid-fix on exactly this; the two ways out are generating real (or nearest-neighbor-upsampled) tiles everywhere the archive claims depth, or accepting the honesty gap. Relevant to FERSPAS collections whose native resolution varies by sub-region.
  - On leaving FAO's live WMTS wrapper behind: independently agrees with the instinct from its own experience — "every 'live wrapper as safety net' idea we've had has turned into its own failure mode." No data on the client-side COG+CORS route (option A/B).

**Source Cooperative (`data.source.coop`) Range-request check, run 2026-09-03 in direct response to the `stars-fd` Cloudflare-drops-large-Range finding**: hfu's reaction to that finding was that it would be a "大災害" (major incident) if hit in production — a browser silently attempting a full-file download instead of a ranged tile read — which shifted his read toward "PMTiles generated by us, hosted on Source Cooperative" looking like the sounder default, *provided* Source Cooperative doesn't share the same failure mode. Tested directly rather than assumed: found a real ~102.5GB file already public there (`protomaps/openstreetmap/tiles/v2/protomaps-basemap-opensource-20230408.pmtiles`, 110,147,520,430 bytes — Protomaps' full OSM-derived planet basemap) and issued ranged `GET`s at the start, a ~90GB mid-file offset, and the very end. All three returned correct `206 Partial Content` with accurate `Content-Range`, and `access-control-allow-origin: *` was present throughout (Source Cooperative's own proxy, self-identified as "Source Cooperative Data Proxy v2.3.4", also sits behind Cloudflare — same vendor as `stars.optgeo.org` — but evidently configured differently, since it doesn't reproduce the drop). This is a real, encouraging data point for hosting our own generated PMTiles on Source Cooperative, though it only tests to ~102.5GB, short of the 190–424GB band where `stars-fd` found the failure — not proof the same can't happen higher up, just no evidence of it at a scale in the same order of magnitude. Since our own PMTiles would be zoom-capped and thus almost certainly well under 100GB regardless, this is more reassurance than a hard ceiling concern for option (C) specifically.

**Still needed before a decision**: confirm the identity of the "stars" hosting platform hfu has in mind for option (B) — now identified as `stars.optgeo.org`; asked the `stars-fd` peer session (2026-09-03) for detail on what it is and whether it fits this use case, reply pending as of this writing. Also still needed: a per-collection file-size/zoom-cap feasibility study for option (C) beyond just ESA WorldCover; and a view on whether/how to raise the CORS gap with FAO CSI regardless of which serving option is chosen.
