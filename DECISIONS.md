### D3 — "Good part" content shortlist: GAEZ-V5's global layers + HIH; WAPOR-3 and ESA WorldCover set aside for now
**Date**: 2026-09-03
**Status**: Shortlist fixed; final pick(s) to convert first still to be narrowed from it.

**What**: After surveying and sizing several candidate families from FERSPAS's 1282-collection catalog (see `HANDOVER.md` and D2), hfu set the working shortlist for what ferspas57 should actually convert and demonstrate:

- **GAEZ-V5**'s global ~1km (30 arc-second) thematic layers — `AEZ33-1KM` and `AEZ57` (Agro-Ecological Zones classification, 33/57 classes), `HWSDV201` (Harmonized World Soil Database), `SLOPE-MED`, `LR-IRR` (irrigable land resources), `ELEV-ALOS-30M`, and the rest of the ~108-collection family. Measured sizes range 28MB (`HWSDV201`) to 521MB (`ELEV-ALOS-30M`), with the flagship classification layers (`AEZ33-1KM`, `AEZ57`) at ~33MB each — a genuinely workable range for a real COG/PMTiles technical exercise, unlike ESA WorldCover's 182GB.
- **HIH** (the Hand-in-Hand initiative) — despite, and in part *because of*, its ~131 collections being fragmented into narrow, country×sector-specific site-suitability scoring layers (e.g. closed-pond fish-farming viability scores per African country: `CAF-FISHFARM-SCORE-CLOSEDPV`, `CMR-FISHFARM-SCORE-CLOSEDPV`, etc.) — see the reasoning below for why fragmentation argues *for* inclusion here, not against it.

Set aside for now (not eliminated, just off the active shortlist):
- **WAPOR-3** — a genuine FAO flagship (WaPOR water-productivity program) and reasonably sized at its L1/L2 continental tier, but judged "too specialized" (専門的すぎる) a subject to be a good first demonstrative target for a general audience.
- **ESA WorldCover** — this session's earlier top pick, now understood as the wrong choice: it is commodity data, already broadly available via AWS Open Data, Copernicus, and Element84 Earth Search independent of FERSPAS entirely. Converting it via FERSPAS wouldn't showcase anything distinctive to FAO or this collaboration.

**Why**: Three criteria converged, refined over the course of this investigation (hfu, verbatim in spirit): *"コンテンツとして魅力的で、データが大きすぎず小さすぎず、技術実証にちょうど良いのがgood partの定義"* (content that's genuinely appealing, data that's neither too big nor too small, technically well-suited to a proof of concept):

1. **Non-commodity, flagship content** — rules out ESA WorldCover; GAEZ (FAO+IIASA, running since the 1980s) and HIH (FAO's cross-cutting 2019 flagship initiative, its own dedicated geospatial platform) both clear this bar.
2. **Size in the workable middle** — ruled out both extremes found during this investigation: GAEZ's own `AEZ33` at native 0.5° resolution (733KB, too coarse/trivial to be a meaningful technical test) and ESA WorldCover (182GB, requiring special-case zoom-capping and infrastructure planning just to attempt). GAEZ's 1km family sits comfortably in between.
3. **A reframing of "handling ease" itself, prompted by hfu**: HIH's fragmentation was initially read (by this session) as a liability weighing against including it — 131 narrow layers are harder to present as one coherent thing than GAEZ's ~108 clean global variables. hfu inverted this reasoning: Staccato's whole premise, per `staccato-spec`, is to move *away* from being another catalog site or geoportal (脱カタログサイト、脱ジオポータル) — and a geoportal's defining failure mode is exactly that fragmented, narrow data gets buried in endless drill-down and never surfaces. HIH's fragmentation is therefore not a reason to exclude it; it is the ideal test case for whether ferspas57's actual differentiator — an AI-generated narrative that visually guides a user to the one specific buried layer they need, rather than a static catalog listing — works in practice. Converting only the easy, already-coherent case (GAEZ) would prove the tile-serving pipeline but not Staccato's actual value proposition. Converting only HIH, conversely, would risk having no clean technical baseline to build the harder UX against. Hence both are on the shortlist together, not as alternatives.

**Technical note**: for GAEZ-V5's global grid family, `mapterhorn-japan-bridge`'s native-leaf-tiles-then-separate-downsampled-pyramid technique (from its Japan DEM PMTiles work — see D2) was flagged by hfu as directly transferable, if GAEZ's various layers need to be presented as one seamless, consistently-tiled family rather than ~108 independently-built archives.

**Within-GAEZ-V5 narrowing (hfu, same day)**: of the candidate layers sized above, the Agro-Ecological Zones classification itself (`AEZ33-1KM` / `AEZ57`) is judged the "catchiest" (キャッチー) — more immediately legible and compelling than terrain or soil layers from the same family. `ELEV-ALOS-30M` (elevation) is specifically deprioritized for a different reason than the others: it would directly overlap (モロ被り) with `mapterhorn-japan-bridge`'s own existing scope (DEM/terrain PMTiles), so pursuing it here would duplicate a sibling dwg7 project's work rather than add something distinct. `HWSDV201` (soil) and `SLOPE-MED` remain on the table but are, so far, less compelling as the lead choice than the AEZ classification layers.

**Still open**: the final narrowing from {GAEZ-V5's AEZ33-1KM/AEZ57 (leading), HWSDV201, SLOPE-MED, LR-IRR; HIH} to whichever collection(s) actually get converted and demoed first; the HIH "AI narrative + visual guidance" UX is a stated direction here, not yet designed in any concrete form; D2's tile-serving architecture question (COG-direct vs. mirrored-COG vs. self-hosted PMTiles vs. FAO's WMTS wrapper) remains independently unresolved and will need an answer for whichever content ends up chosen here.

### D2 — Tile-serving architecture for FERSPAS raster collections: options surveyed, not yet decided
**Date**: 2026-09-03
**Status**: Open. Investigation and option-framing only — no option has been chosen.

**What we found by surveying the live catalog** (paged all 1282 collections via `https://data.review.fao.org/geospatial/search/stac/collections`):

- No orthophoto/aerial-imagery collection exists anywhere in the current 1282. The Niedersachsen DOP dataset hfu noted in `UNopenGIS/7#932`'s June 2026 comment (external data, CC-BY-4.0, provided by Germany's Niedersachsen state survey office LGLN, not FAO) was present in FERSPAS's catalog then but is **confirmed absent now** — removed at some point between June and September 2026, not merely renamed or missed by keyword search.
- Across all 33 top-level `fao-gismgr:*` sub-catalogs (sampled one representative item per prefix), asset structure is strikingly uniform: every item has a `data` asset (Cloud-Optimized GeoTIFF) plus `preview`/`thumbnail` assets served through a single FAO-run WMTS endpoint, `https://data.apps.fao.org/map/wmts/wmts`. No vector assets were found anywhere in the sample. This means FERSPAS's practical heterogeneity (as STAC-the-spec allows) is much lower than the STAC-in-general case — the catalog appears to be generated by one internal FAO GISMGR pipeline that normalizes everything to this same shape.
- That WMTS endpoint (self-identified in its `GetCapabilities` response as **"FAO WMTS WRAPPER"**, provider **FAO CSI**, contact **Mohamed Megahed** — the same team behind the June 2026 DWG5 presentation) serves every sampled layer through the standard `GoogleMapsCompatible` (Web Mercator, 256px, z0–z24) tile grid — i.e. it is already a de facto XYZ tile server for the whole catalog, confirmed working (`200 image/png`) against layers from `ESA`, `CRTB`, `GAEZ-V5`, `GLOSIS`, `HIH`, and `WAPOR-3`.
- Measured performance of that WMTS wrapper (ESA WorldCover 2020, `fao-gismgr:ESA:raster:maps:WC2020`): 200ms–4s per tile depending on zoom, one transient 503 observed near native-resolution zoom (not reproducible on retry), and — critically — `cf-cache-status: DYNAMIC` on every request including immediate repeats, meaning Cloudflare is not edge-caching these tiles at all despite a `Cache-Control: public, max-age=3600` header. Every tile request reaches FAO's live App Engine backend.
- The underlying COG itself (`gs://fao-gismgr-esa-data/DATA/ESA/MAP/ESA.WC2020.tif`, 195,668,306,548 bytes ≈ 182GB, global, ~9.28m/px native resolution) is a genuinely well-formed Cloud-Optimized GeoTIFF: 256×256 internal tiling, LZW compression, and a full 15-level internal overview pyramid (down to 132×66px). `storage.googleapis.com` correctly serves HTTP range requests (`206 Partial Content`, `Accept-Ranges: bytes`). **However, the bucket has no CORS configuration** (`access-control-allow-origin` absent from every response tested) — so a browser-side MapLibre COG reader cannot range-read it directly today, even though the file itself is structurally ready for that access pattern.

**Options on the table** (none selected yet):

- **(A) Direct client-side COG range access against FAO's own GCS bucket.** Best long-term outcome — no duplication, no extra infrastructure, matches Staccato's "reference, don't copy" philosophy most purely. Blocked today solely by the missing CORS header, which is FAO's to fix, not ours.
- **(B) Mirror the raw COG (unconverted) onto our own storage with CORS enabled**, e.g. GitHub or Source Cooperative (hfu: exact platform still to be confirmed — "stars" mentioned but not yet resolved to a real service name). Framed explicitly by hfu as a *"technical hostage"* (技術的人質): a deliberately temporary, transparent mirror we would decommission the moment FAO enables CORS on the original. Open concerns raised: (1) the mirror's own CDN may not outperform GCS+Cloudflare, so this may not even solve the performance problem, only the CORS problem; (2) mirroring FAO's raw data onto third-party infrastructure without their buy-in risks reading as presumptuous even under a permissive license, and must be proposed to FAO transparently rather than done silently, per this repo's "Positive intent" stance.
- **(C) Convert to our own zoom-capped PMTiles and host statically**, mirroring `layers-martin`'s static-hosting pattern but adding an actual conversion step (since, unlike GSI's source, FERSPAS's source is COG, not already-tiled). Full performance and hosting control; smallest diplomatic footprint since it's a clearly-derived, attributed display product rather than a raw-data copy; but full-native-resolution global PMTiles is infeasible for something the size of ESA WorldCover (182GB) — would need a deliberately capped max zoom (and possibly per-collection sizing work) to be practical.
- **(D) Consume FAO's existing WMTS wrapper directly, live.** Zero engineering cost, works today, but the measured latency (up to several seconds/tile) and complete absence of edge caching make it unsuitable as a production path — and routing real end-user traffic through it risks being a real burden on FAO CSI's own infrastructure, which cuts against this repo's reciprocity framing. Reasonable only as a low-volume prototyping/demo path, not a shipped architecture.

**Why this is being recorded now, unresolved**: hfu's framing is that this design reasoning — done logically, fairly, and tastefully — may itself be a piece of value this repo delivers, independent of which option is ultimately chosen; possibly even shareable back to FAO CSI as constructive feedback (the CORS gap in particular is something fixing would benefit the whole ecosystem, not just this repo). Recording the option space and evidence now, before forcing a premature decision, keeps that reasoning legible for whoever continues it.

**Two clarifications from hfu on 2026-09-03, refining but not resolving the above**:
- On option (B)'s "duplication" question: whether a mirror is *legally* permitted by FERSPAS's license is a separate axis from whether making one *without telling FAO* is the right thing to do. hfu's framing: doing it silently would be legally fine but relationally 水臭い (distant/standoffish — the kind of move that quietly erodes trust between collaborators) given this repo's stated reciprocity stance. If a mirror is ever built, it should be proposed to FAO transparently, not simply shipped.
- (B) and (C) are confirmed as the two main contenders. But hfu explicitly named keeping (A) and (D) "in view" rather than discarding them — i.e. staying ready to adopt (A) the moment FAO fixes CORS, and treating (D) as a legitimate (if limited) fallback rather than a non-option — as itself characteristic of dwg7's way of working: holding the full option space in mind rather than collapsing to a single path prematurely.

hfu also decided (B) and (C) both warrant actual hands-on prototyping, as tests of two different technologies rather than a pick-one call: (B) tests the current state of client-side COG-in-MapLibre reading technology; (C) tests the practical feasibility of dwg7's static/distributed-hosting vision applied to a genuine COG-sourced (not already-tiled) dataset. Two peer sessions were consulted for this:

**`stars-fd` on `stars.optgeo.org`** (asked 2026-09-03 what the platform is and whether it fits option B): it is hfu's personal Raspberry Pi (aarch64, Debian 13) running Martin, config-of-record in `hfu/stars` on GitHub with `stars-fd` as PR gatekeeper, exposed via a Cloudflare named tunnel as `stars.optgeo.org` (tiles/styles, Martin) and `depot.optgeo.org` (raw file browsing, Caddy, already `Access-Control-Allow-Origin: *`). Findings directly relevant to D2:
  - Martin's COG support is an opt-in `unstable-cog` Cargo feature **not present in the current production build (v1.14.0)** — so Martin-as-COG-tile-source is not available today regardless of hosting choice.
  - **Critical, previously-unknown risk for option (B)**: Cloudflare's proxy in front of `depot.optgeo.org` silently drops `Range` requests above some threshold between 190GB and 424GB, returning `200` (whole file) instead of `206`. Verified directly against origin (fine at 424GB) vs. through the public Cloudflare-fronted URL (76KB→206 OK, 190GB→206 OK, 424GB→200/Range ignored). A browser attempting to range-read a COG above that threshold through this specific host would try to download the whole file instead — unusable for datasets in that size class (ESA WorldCover's 182GB is close to, but apparently under, the danger zone; would need re-verification specifically, not assumed safe by proximity alone).
  - Option (C) is *not* subject to this problem: Martin does the range-reading server-side and returns normal tile responses to the client, regardless of source file size. Already proven at this kind of scale — `stars.optgeo.org` currently serves 168–198GB of Overture Maps data this way (as a remote PMTiles source, no local copy).
  - Capacity: 397GB free of 1.8TB on the host filesystem as of this check (fluctuates).
  - `stars-fd`'s own assessment: for a large (100GB+) permanent COG mirror, a purpose-built platform (e.g. Source Cooperative, S3-based, designed around CORS+Range) is more straightforward than a single Raspberry Pi with the Cloudflare quirk above; for small-to-medium (tens of MB–a few GB) PMTiles, `stars.optgeo.org` is already a proven, comfortable fit (cites the Vientiane zoning-data project). It explicitly asked that any concrete next step be run past hfu first, since the host is shared infrastructure across several dwg7 projects.

**`mapterhorn-japan-bridge/japan-geotiff-dem`** (asked 2026-09-03 for its GeoTIFF→PMTiles conversion know-how, for option C — it has built a ~314GB clustered PMTiles archive from national-scale GSI elevation DEMs at 1m/5m/10m). Its data is continuous (elevation), ours would be discrete (classification), so not everything transfers, but the operational lessons are directly usable:
  - Tooling: GDAL/rasterio (Python) for reprojection/aggregation, Go `pmtiles` CLI (`cluster`/`merge`/`verify`/`show`) for archive assembly, Python `pmtiles` library for bulk merges. No single-pass `gdal2tiles`-style descent.
  - Architecture lesson (conditional): if source resolution/coverage varies across the collection, build native-resolution leaf tiles first, then a *separate* downsampled-pyramid pass reading from those leaves — not relevant if a given FERSPAS collection is uniform-resolution throughout, but worth checking per collection before assuming a simple top-down build works.
  - Infra gotchas worth pre-empting rather than rediscovering: `go-pmtiles` respects `TMPDIR` but SSH sessions often carry a stale one that silently wins over `setdefault()` — force-override and confirm with `df` (cost them a corrupted 310GB archive once); always run `pmtiles verify` after cluster/merge (cheap, catches corruption `show` misses); `rsync` without `--whole-file` balloons memory doing delta-checksums against any pre-existing partial file at the destination; never trust a bare `glob()` to confirm a merge input is complete — use a per-region completion manifest instead (a naive glob once shipped them a silent ~25%-of-country gap); keep leaf-tile and pyramid-tile output in visibly distinct namespaces (a naming collision once cost them 3,344 tiles to a cleanup-script bug).
  - **For discrete classification data specifically** (directly relevant to something like ESA WorldCover's 11 land-cover classes): skip terrarium-style RGB float-packing (that's an elevation-only trick); prefer single-band tiles with the raw class code as the pixel value, recolored client-side via a MapLibre `raster-color`/match expression against the STAC item's `classification:classes` legend — keeps tiles smaller, keeps raw codes queryable, and allows restyling without regenerating tiles. Baking colors into RGB at generation time is the simpler-client alternative but forecloses both of those. Always use **lossless** WebP for class-code data — lossy compression blends/corrupts values at class boundaries. Expect favorable compression versus elevation-tile experience, since large uniform regions (ocean, forest blocks) collapse very well under lossless WebP run-length-style encoding.
  - **A real constraint to design around**: PMTiles/TileJSON support only one global `maxzoom` per archive — there is no per-region maxzoom anywhere in the stack. If parts of a collection only have genuine native detail to a shallower zoom than others, the archive will over-declare depth for those regions and deep-zoom requests there will 204. Mapterhorn is mid-fix on exactly this; the two ways out are generating real (or nearest-neighbor-upsampled) tiles everywhere the archive claims depth, or accepting the honesty gap. Relevant to FERSPAS collections whose native resolution varies by sub-region.
  - On leaving FAO's live WMTS wrapper behind: independently agrees with the instinct from its own experience — "every 'live wrapper as safety net' idea we've had has turned into its own failure mode." No data on the client-side COG+CORS route (option A/B).

**Source Cooperative (`data.source.coop`) Range-request check, run 2026-09-03 in direct response to the `stars-fd` Cloudflare-drops-large-Range finding**: hfu's reaction to that finding was that it would be a "大災害" (major incident) if hit in production — a browser silently attempting a full-file download instead of a ranged tile read — which shifted his read toward "PMTiles generated by us, hosted on Source Cooperative" looking like the sounder default, *provided* Source Cooperative doesn't share the same failure mode. Tested directly rather than assumed: found a real ~102.5GB file already public there (`protomaps/openstreetmap/tiles/v2/protomaps-basemap-opensource-20230408.pmtiles`, 110,147,520,430 bytes — Protomaps' full OSM-derived planet basemap) and issued ranged `GET`s at the start, a ~90GB mid-file offset, and the very end. All three returned correct `206 Partial Content` with accurate `Content-Range`, and `access-control-allow-origin: *` was present throughout (Source Cooperative's own proxy, self-identified as "Source Cooperative Data Proxy v2.3.4", also sits behind Cloudflare — same vendor as `stars.optgeo.org` — but evidently configured differently, since it doesn't reproduce the drop). This is a real, encouraging data point for hosting our own generated PMTiles on Source Cooperative, though it only tests to ~102.5GB, short of the 190–424GB band where `stars-fd` found the failure — not proof the same can't happen higher up, just no evidence of it at a scale in the same order of magnitude. Since our own PMTiles would be zoom-capped and thus almost certainly well under 100GB regardless, this is more reassurance than a hard ceiling concern for option (C) specifically.

**Still needed before a decision**: confirm the identity of the "stars" hosting platform hfu has in mind for option (B) — now identified as `stars.optgeo.org`; asked the `stars-fd` peer session (2026-09-03) for detail on what it is and whether it fits this use case, reply pending as of this writing. Also still needed: a per-collection file-size/zoom-cap feasibility study for option (C) beyond just ESA WorldCover; and a view on whether/how to raise the CORS gap with FAO CSI regardless of which serving option is chosen.

### D1 — Repo founded: FERSPAS↔Staccato technical collaboration, split from UNopenGIS/7#932
**Date**: 2026-09-03
**What**: Created `dwg7/ferspas57` (public, CC0 1.0) at hfu's request, made during a `dwg7/staccato-ecosystem`-session Claude Code conversation. Scope: write a `martin catalog`-compatible interface for FERSPAS (FAO's Essential Remote Sensing Data Product Portal, native interface STAC), starting with FERSPAS's orthophoto products, so Staccato's Library can demonstrably reach FERSPAS data. This is the technical follow-through on [`UNopenGIS/7#932`](https://github.com/UNopenGIS/7/issues/932) (DWG5×DWG7 exploration), split out into its own founding issue [`UNopenGIS/7#997`](https://github.com/UNopenGIS/7/issues/997) and its own repo because the work is implementation-shaped (real code, a real conversion pipeline) rather than spec-shaped or value-proposition-shaped. Scaffolded with `README.md`, `CLAUDE.md`, `HANDOVER.md`, `DECISIONS.md`, `LICENSE` (CC0 1.0, copied verbatim from `dwg7/staccato-ecosystem`), matching the established `dwg7` per-project convention (dedicated repo, dedicated session, `HANDOVER.md`/`CLAUDE.md` as onboarding). English throughout, unlike `staccato-ecosystem`'s Japanese-primary content policy, because this repo is explicitly international/FAO-facing.
**Why**: `staccato-spec`'s `catalog-integration.md` §10 already commits to treating STAC as a conversion source rather than Cartographer's primary model; this repo is the first real-world test of that commitment, prompted by DWG 5's June 2026 presentation on FAO/ITU Geo-AI systems identifying FERSPAS as the strongest concrete-collaboration candidate of the three systems surveyed. It also has a real external forcing function: [`UNopenGIS/7#994`](https://github.com/UNopenGIS/7/issues/994), a FAO CSI talk on 2026-09-28 that cites this collaboration directly. Positioned explicitly as a reciprocal, good-faith technical contribution — not a one-sided data pull — in response to FAO CSI's unusually detailed and generous June 2026 technical presentation (see `CLAUDE.md`'s "Positive intent" section for the fuller framing hfu asked to have documented here).

**Knowledge-flow split** (also recorded in `CLAUDE.md`): learnings from this repo are expected to flow to different places depending on their nature — STAC↔martin-catalog technical/architectural patterns to `UNopenGIS/staccato-spec`; collaboration-process/value-proposition learnings to `dwg7/staccato-ecosystem` (this repo is that repo's international-cooperation counterpart to `dwg7/chukei`); generic `dwg7` technical patterns to `dwg7/cafebabe`. Nothing should accumulate here indefinitely without eventually being routed onward.
